
需要一个更全面和强大的数据库，来提供更多的召回手段，这是由于为解决 RAG 中召回精度不高的痛点，需要采用多种方法混合搜索。除了向量搜索之外，还应该包含关键词全文搜索、稀疏向量搜索，乃至支持类似 ColBERT 这样 Late Interaction 机制的张量搜索。

- 关键词全文搜索是实现精确查询必不可少的手段，通过关键词全文搜索，可以查看跟查询匹配的关键词，从而更直观地了解检索到该文档的原因，对于排序的可解释性也很重要。除了需要能够处理海量数据之外，为符合 RAG 召回的需要，还必须提供默认基于 Top K Union 语义的搜索机制，这是由于 RAG 的查询输入通常不是几个关键词，而是整句话。目前市面上大多数声称提供 BM25 和全文搜索能力的数据库，实现的都是阉割版本，既无法高性能搜索海量数据，也无法提供有效召回，不具备企业级服务能力。
- 在若干问答数据集的评测中，联合关键词全文搜索、稀疏向量、以及向量搜索 3 种召回方式，取得了 SOTA 的结果。
- 张量搜索，来自于以 ColBERT 为代表的 Late Interaction 机制。过去以 Cross Encoder 为代表的 Reranker 模型，能够捕捉查询和文档之间的复杂交互关系，因此相比向量搜索能够提供更精准的搜索排序结果。但是其缺点在于，由于需要在查询时对每个文档和查询共同经过 Embedding 模型来编码，这使得排序的速度非常慢，因此 Cross-Encoder 只能用于最终结果的重排序。而类似 ColBERT 这样的模型，仍然把文档在索引阶段就编码好，这一点类似于向量搜索，但不同之处在于，它把文档的每个 Token 都用单独的向量表示，因此是用许多向量或者一个张量来表示一个文档，在排序计算时，所有 Token 之间的向量都需要做交叉计算，这一点跟 Cross Encoder 的机制类似，因此比向量搜索损失的信息更少，召回精度更高。而相比 Cross Encoder，它的性能要好得多，因为在查询期间无需对每个文档进行编码， 所以可以理解为既拥有接近 Cross Encoder 的召回精度，也拥有接近向量搜索的性能，这样可以在召回阶段就引入更好的模型，具有非常强的实际操作价值。结合张量搜索和关键词全文搜索，不失为一种非常值得采用的混合搜索能力。作为数据库来说，同样需要为这样的能力提供选择。

近期 OpenAI 收购了数据仓库公司 Rockset，这背后的逻辑，其实并不在于数据仓库本身对于 RAG 有多么大的价值，而是相比其他数据仓库，Rockset 更是一个索引数据库，它对表的每列数据都建立了倒排索引，因此可以提供类比于 Elasticsearch 的关键词全文搜索能力，再配套以向量搜索，原生具备这两类混合搜索能力的数据库，在当前阶段，就已经没有多少选择了，再加上 Rockset 还采用了云原生架构，两点结合，是 OpenAI 做出选择的主要原因。

### 其他环节的优化

1. 需要有单独的数据抽取和清洗模块，来针对用户的数据，进行切分。切分的粒度，需要跟最终搜索系统返回的结果进行迭代。数据抽取模块，需要考虑到用户的各种不同格式，包含复杂文档例如表格处理和图文等，因此它必须依托于若干模型才能完成任务。高质量的数据抽取模块，是保证高质量搜索的前置条件。这部分可以类比为现代数据栈的 ETL，但却比 ETL 更加复杂，后者是以 SQL 为核心的的确定性规则系统，而前者则是以各种文档结构识别模型为核心的非标准化体系。
2. 抽取出的数据，在送到数据库索引之前，还可能需要若干预处理步骤，包括知识图谱构建，文档聚类，以及针对垂直领域的 Embedding 模型微调等。这些工作，本质上是为了辅助在检索阶段提供更多的依据，从而让检索更加精准。这个步骤不可或缺，它是针对用户的复杂提问，例如多跳问答，意图不确定，以及垂直问答等情况下的必要手段。通过把文档中包含的内部知识以多种方式组织，才能确保在召回结果包含所需要的答案。
3. 检索阶段分为粗筛和精排。精排通常放在数据库外进行，因为它需要不同的重排序模型。除此之外，还需要对用户的查询不断改写，根据模型识别出的用户意图不断改写查询，然后检索直至找到满意的答案。

其他问题

### 否定语义失效（“非 A → A”）

本质： embedding 不理解“否定/排除”语义，搜“非 A”却召回“A”

解决： 检索前（理解/改写）、检索中（控制召回）、检索后（过滤/重排）

Query rewrite、BM25（hybrid + 关键词 / BM25 过滤）、LLM rerank、多向量表示（ColBERT 等）、metadata filtering

### 比较/条件语义无法处理

例如：

- “A 和 B 的区别”
- “A 的优点而不是缺点”
- “在条件 X 下的 Y”

**常见坏结果：**

- 返回一堆 A，或者一堆 B，**但不是比较**
- 条件语义（under X）完全丢失

**原因：**

- Embedding 不会理解复杂逻辑
- 检索结果中 A 和 B 分散不在同一 chunk

**解决方式：**

- Query 重写（"A vs B difference"）
- 多 Query Multi-vector retrieval
- chunk regrouping（按主题/按实体聚合）
- reranker 强制找比较项

### 粒度问题（Chunking 过大/过小）

**Chunk 太大：**

- 高相似度，召回不准（因为噪音多）
- LLM 无法从大段内容中找关键信息

**Chunk 太小：**

- 信息不完整
- 无法保持上下文关系

**解决方向：**

- 动态 chunking（按语义边界自动切分）
- Recursive chunking（长→短两级切分）
- 按文档结构（标题/小节）切分

### 召回不全（Recall Poor）

即使 embedding 模型很强，也可能：

- 找不到正确内容
- 高质量文档没被检索出来
- Entity mismatch（用户说“合同终止”，文档写“协议解除”）

**原因：**

- 词汇不对齐
- 埋没在长文档中
- 向量相似度弱

**解决：**

- Query Expansion（同义词扩展）
- Multi-Query Retrieval
- Reranker 提升 recall
- 建立 Domain Thesaurus（内部术语同义词库）

### 召回过多噪音（Precision 差）

用户问“如何续签合同？”

召回一堆：

- 合同模板
- 合同定义
- 完全无关的合同类型

**原因：**

- embedding 范围太宽
- chunk 中噪音太多
- 文档主题不明确

**解决：**

- 更好的 chunk 标签（metadata）
- 标签检索 + 向量检索
- reranker 限制内容主题

### 时间语义问题（Temporal Reasoning 失败）

RAG 经常会出现：

用户问：

> “当前有效的价格是多少？”

召回了：

- 以前过期的价格
- 混杂多版本数据

**原因：**

- 向量检索不理解时间
- Chunk 里时间信息混乱

**解决：**

- metadata：version, timestamp
- 检索策略：按最新排序
- 使用 LLM reranker 做 Temporal Filtering

### 数字/代码/符号检索失败

例如：

- 产品 ID
- 规范编号
- 代码参数
- 类似“GB/T 2828.1-2012”

Embedding 对这些非常弱，会召回无关信息。

**解决：**

- 添加 exact-match index（keyword index）
- hybrid（BM25 + vector）
- 将数字/ID 做特殊 token 处理

### 用户 query 过短或过宽导致召回模糊

比如：

- “发票”
- “安全要求”
- “合同问题”

这些太广，导致：

- 几乎整个库的内容都相似度很高
- 导致噪音巨大

**解决：**

- Query Clarification/Rewriting
- Intent Classification
- 业务词典（domain taxonomy）

#### 幻觉（Hallucination）无法避免

RAG 并不能彻底阻止 LLM 幻觉，它只“降低概率”。常见情况：

- 文档未覆盖的内容 → LLM 自动瞎编
- 检索到了错误内容 → LLM 认为是真的
- 多个文档矛盾 → LLM 随便选一个

**解决：**

- Retrieval Grounded Generation（严格引用）
- 让 LLM 判断“是否有支持来源”
- answerability detection（无答案也要回答“无信息”）

### 多轮对话中的上下文漂移

用户：

1. “告诉我 A 的风险”
2. “那 B 呢？”

RAG 会：

- 把第二个 query 当独立查询
- 或忽略上下文
- 或把 A+B 全部召回

**解决：**

- Query Rewriting with memory
- Conversation state tracking
- 对话实体抽取（entity tracking）

### 跨文档关联失败

> “A 文件和 B 文件关于风险管控的共同要求是什么？”

RAG 默认只处理单个 chunk，因此：

- 没法自动“跨文件合并信息”
- 逻辑推理能力不足

**解决：**

- 多文档合并（post-retrieval merging）
- LLM 进行 cross-document reasoning
- GraphRAG（基于知识图谱）

### 专业词汇实体识别失败（NER Domain Shift）

- 医疗术语
- 金融风控指标
- 法规条款编号
- 企业内部术语

Embedding 不能识别 domain-specific entity。

- Domain finetuning（做 embedding 域适配）
- 领域词典 + 规则匹配
- GraphRAG 实体节点

### 多跳

1. 把“多跳”拆成多次单跳：通过 query decomposition（把复杂问题拆成子问题）或 iterative retrieval（基于中间结果继续检索）。
2. 检索与阅读分工：用 Enhanced Retriever 找候选段，再用强生成器/融合阅读器（FiD、Fusion-in-Decoder、Seq2Seq reader）融合证据并推理。
3. 重排与过滤：先检索 top-k，再用 reranker（cross-encoder）把真正相关的放前面，减少噪声给 reader。
4. 利用中间变量：把生成器的中间事实（entity list / intermediate answer）回写成新的检索 query（feedback loop）。
5. 必要时用结构化知识：把文本检索补上实体链接、知识图谱或关系查询，能极大降低跳数复杂度。
6. ReAct 模式，增加 LLM 的“思考”环节，让它在每次检索后进行自我校准和推理
