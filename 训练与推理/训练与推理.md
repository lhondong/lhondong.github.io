# 训练与推理系统深入

## 0. 显存与通信：贯穿全文的两把尺子

在具体讲框架之前，先把账算清楚，后面每个框架都是在这两本账上做不同的取舍。

### 0.1 显存账本：一个 7B 模型的 Adam 全参训练到底要多少显存

设模型参数量为 $\Phi$。混合精度训练（FP16/BF16 计算 + FP32 主权重）下，显存被称为"模型状态"（model states）的部分由四块组成，每块的字节数：

| 组成 | 精度 | 每参数字节数 | 说明 |
|---|---|---|---|
| 参数（用于前向/反向计算） | FP16/BF16 | 2 | 实际参与矩阵乘法的权重 |
| 梯度 | FP16/BF16 | 2 | 反向传播产生 |
| 优化器状态 - FP32 主权重 | FP32 | 4 | 防止 FP16 更新时精度丢失（Loss Scaling 配合使用） |
| 优化器状态 - Adam 一阶矩（momentum） | FP32 | 4 | |
| 优化器状态 - Adam 二阶矩（variance） | FP32 | 4 | |

合计

$$2+2+4+4+4 = 16\Phi \text{ 字节}$$

其中优化器状态占 $12\Phi$（75%）。这就是 Infra.md 里"优化器状态是参数的 8x"这个经验说法的来源（$12\Phi$ 相对 $2\Phi$ 的 FP16 参数是 $6\times$，相对 $4\Phi$ 的 FP32 权重是 $3\times$，具体倍数取决于对比基准，但结论一致：**优化器状态而非参数本身，才是显存的大头**）。

举例：7B 模型，

$$16\Phi = 16 \times 7\times10^{9} \approx 112\text{GB}$$

一张 80GB 显卡根本放不下"模型状态"本身，这还没算激活值——这就是为什么 7B 模型全参微调也需要多卡分片（ZeRO/FSDP）而不能简单 DDP。

**激活值**是另一块随 batch size × 序列长度 × 层数近似线性增长的显存，且不像模型状态那样"知道总量"——同样的模型，序列长度从 4K 拉到 128K，激活值可能从几 GB 涨到几十上百 GB。这正是 **Activation Checkpointing（重计算）** 存在的原因：反向传播需要用到前向的中间激活值来算梯度，正常做法是全部存下来，Checkpointing 则只保存少数几个"检查点"层的激活，其余的在反向时**现算一遍前向**，用计算时间换显存空间。

**为什么"每隔 $\sqrt{L}$ 层设一个检查点"是经典最优解**：设模型有 $L$ 层，如果每隔 $k$ 层保存一次检查点激活，反向传播到某一层时，需要从最近的检查点重新前向计算最多 $k$ 层来还原出当前层的激活值。总显存占用近似正比于保存的检查点数 $L/k$（每个检查点存一份激活）；总额外计算量方面，每次反向平均要重算 $k/2$ 层，整个反向过程重算的层数总和 $\approx L$（因为一共只有 $L$ 层要重算，检查点密度不影响这个总量，但会体现在"重算峰值"的分布上）。真正的权衡在**显存 × 重算次数**这个联合优化上——如果 $k$ 太小，检查点存得多，显存占用接近不做 checkpointing；如果 $k$ 太大，虽然显存降到最低，但反向时单次要现算很多层，重算开销集中爆发。设总显存代价近似为

$$\text{Memory}(k) \approx \frac{L}{k} + k$$

对 $k$ 求最小值，由均值不等式 $\frac{L}{k}+k \geq 2\sqrt{L}$（当且仅当 $\frac{L}{k}=k$，即 $k=\sqrt{L}$ 时取等号），可以证明当

$$k \approx \sqrt{L}$$

时，显存占用达到最优的 $O(\sqrt{L})$（而不做 checkpointing 时是 $O(L)$）——这就是"每隔 $\sqrt{L}$ 层设一个检查点"这个经验法则的数学来源，能把激活值显存从随层数线性增长压到随层数的平方根增长，代价是反向传播的计算量大约增加 33%（相当于多做一次前向的三分之一左右，具体系数取决于前向/反向各自耗时比例）。

Megatron 提出的 **Selective Recomputation** 在这个基础上更进一步：不是简单"每隔 $k$ 层整体重算"，而是精细区分层内不同算子——只对"重算成本低、显存占用大"的部分（比如 Attention 里的 softmax、dropout 这类逐元素操作，重新算一遍很便宜但省下的激活值显存不小）做重计算，对"重算成本高"的部分（如大矩阵乘 GEMM，重新算一遍开销很大）仍然保留激活值不做重算，取得计算开销和显存节省之间比"整层重算"更精细的平衡点。

### 0.2 通信账本：四种基础通信原语

* **All-Reduce**：所有卡各自持有一份数据，规约（求和/求均值）后每卡都拿到相同的完整结果。典型场景：DDP 的梯度同步、TP 内 Attention/MLP 输出的求和。
* **All-Gather**：每卡持有数据的一个分片，操作后每卡都拿到所有分片拼接起来的完整数据。典型场景：ZeRO-3/FSDP 用参数分片临时拼出完整层参数。
* **Reduce-Scatter**：每卡持有完整数据，规约后**每卡只保留结果的一个分片**（而不是像 All-Reduce 那样人人都拿完整结果）。典型场景：ZeRO-2/3 反向时把完整梯度规约后按分片保留。
* **All-to-All**：$N$ 张卡，每张卡都要把自己数据的一部分发给其余每一张卡，同时从其余每张卡收一部分数据回来，像是"全员互相寄快递"。典型场景：MoE 的 token 路由到 expert、DeepSpeed-Ulysses 的序列并行转置。

理解这四个原语的通信量级（是否与卡数无关、是否随卡数增长）是判断一个并行策略能否 scale 到几百上千卡的核心依据，下面每一节都会具体套用。

### 0.3 混合精度与低精度训练：不只是"把 FP32 换成 FP16"

前面显存账本里已经用到了"参数用 FP16、优化器状态用 FP32"这个设定，这里把背后的机制讲完整——低精度训练省的是显存和带宽，但精度问题如果处理不好，会直接导致 loss 发散，几乎每次大模型训练事故排查都会牵扯到这里。

* **FP16 的问题与 Loss Scaling**：FP16 是 1 位符号 + 5 位指数 + 10 位尾数，指数位少意味着**表示范围窄**（最小正规数约 $6\times10^{-5}$），训练中大量梯度值（尤其是接近收敛、梯度很小时）会小到直接下溢为 0，梯度信息完全丢失。**Loss Scaling** 的解法很直接：反向传播前，把 loss 乘上一个较大的缩放系数 $S$（比如 $2^{14}$），根据链式法则，这会让所有梯度也同步放大 $S$ 倍，从而"挤"到 FP16 能表示的数值范围里；更新参数前再把梯度除回 $S$ 还原真实大小。**动态 Loss Scaling（Dynamic Loss Scaling）**是实践中的标准做法：从一个较大的 $S$ 开始，如果连续若干步都没有出现梯度上溢（Inf/NaN），就尝试把 $S$ 加倍（争取覆盖更宽的动态范围）；一旦检测到某一步梯度出现 Inf/NaN（说明 $S$ 太大导致上溢），就跳过这一步参数更新，把 $S$ 减半再重试。这套"自动探测安全上界"的机制让训练不需要为每个任务手动调 $S$。
* **BF16 为什么更省心**：BF16 同样是 16 位，但采用 8 位指数 + 7 位尾数——指数位数和 FP32 完全一样（表示范围和 FP32 相当，不会出现 FP16 那种大范围下溢/上溢问题），代价是尾数位更少（精度低于 FP16）。这意味着 **BF16 通常不需要 Loss Scaling**，训练稳定性工程量更小，是目前大模型预训练的主流选择；FP16 在同样字节数下数值精度略高，但需要更精细的 Loss Scaling 调参，两者是"表示范围 vs 精度"的直接取舍。
* **Master Weights 为什么必须是 FP32**：随着训练推进，单次参数更新量（学习率 × 梯度）往往远小于参数本身的量级，如果参数一直以 FP16/BF16 存储，很多次小幅度更新会因为精度不够被直接舍入抹平（相当于"不断加很小的数但总数值没变"），模型会学不动。解法是额外维护一份 **FP32 主权重（Master Weights）**：每步更新在 FP32 精度上进行，更新完成后再转换出一份 FP16/BF16 的权重副本供前向/反向计算使用——这也是 0.1 节里"参数"和"优化器状态里的 FP32 主权重"两笔账分开算的原因。
* **FP8 训练：Scale 校准是核心难点**（Hopper Transformer Engine 起做训练侧标配，已核实机制）：FP8 只有 8 位，动态范围比 FP16/BF16 更窄得多，且模型里不同 tensor（不同层的激活、不同层的梯度）的数值分布差异很大，**用同一个 Loss Scaling 系数已经不够用**，必须给每个 FP8 tensor 单独配一个缩放系数（scale factor）。常见的两种校准策略：
  * **Delayed Scaling（延迟缩放）**：维护一个滑动窗口，记录最近若干步里该 tensor 的绝对值最大值（记为 $\text{amax}$）历史，用这个历史窗口里的统计值来决定当前这一步的 scale——好处是把"算 $\text{amax}$"和"用 scale 做量化"这两个操作解耦，不用在关键路径上等当前步的 $\text{amax}$ 算出来才能继续，性能最好；风险是用的是"过去"的统计值，如果数值分布突然剧烈变化（正是训练不稳定时最容易发生的情况），缩放系数可能跟不上，造成精度损失。
  * **Current/Per-Tensor Scaling（即时缩放）**：就地（just-in-time）实时计算当前 tensor 的 $\text{amax}$ 再决定 scale，精度更好但会在关键路径上引入额外的同步开销；这是目前 Hopper/Blackwell 上被推荐替代 Delayed Scaling 的方案（Delayed Scaling 因为精度风险已经不再是首选）。
  * 训练里通常对输入/权重用 **E4M3**（4 位指数 + 3 位尾数，精度更高、范围较窄）格式、对梯度用 **E5M2**（5 位指数 + 2 位尾数，范围更宽，因为梯度数值波动更大）格式，这种混合格式的选择本身也是"表示范围 vs 精度"权衡的体现。
  * **Per-block scaling**：比全 tensor 共享一个 scale 更细粒度的方案是给 tensor 内部的每个小块（block，比如 128 个数一组）分别配一个 scale，进一步降低量化误差，是 DeepSeek-V3 等模型训练里采用的方案，代价是需要在计算时额外处理这些块级 scale 的对齐。

## 1. 数据并行的演进：DP → DDP → ZeRO → FSDP

### 1.1 朴素 DP 与 DDP

* **朴素 DP（`nn.DataParallel`）**：单进程多线程，主卡负责 scatter 输入、gather 输出、reduce 梯度，主卡显存/带宽成为瓶颈，Python GIL 限制吞吐，现在基本不用，但要知道它是 DDP 的对照组——DDP 几乎所有设计都是在解决朴素 DP 的这几个问题。
* **DDP（`DistributedDataParallel`）**：多进程（每卡一个进程），每卡持有完整模型副本，前向/反向独立计算，只在反向时同步梯度。

#### 深入：Ring All-Reduce 到底在做什么、为什么通信量与卡数无关

这是理解 DDP 可扩展性的关键，值得完整推导一遍。设 $N$ 张卡，每张卡要同步的梯度总大小为 $S$。

**朴素做法（Naive All-Reduce）**：选一张卡当"总管"，其余 $N-1$ 张卡把自己的梯度发给它，总管求和后再广播回 $N-1$ 张卡。总管这张卡要收 $N-1$ 份数据、发 $N-1$ 份数据，通信量随 $N$ 线性增长，总管的带宽是全局瓶颈——这正是朴素 DP 的问题所在。

**Ring All-Reduce 的做法**：把 $N$ 张卡连成一个环（卡 $0 \to$ 卡 $1 \to \cdots \to$ 卡 $N-1 \to$ 卡 $0$），且把每张卡的梯度数据切成 $N$ 份小块。整个过程分两个阶段，每阶段各走 $N-1$ 步：

1. **Reduce-Scatter 阶段**（$N-1$ 步）：每一步，每张卡把自己当前持有的某个数据块发给环上的下一张卡，同时从上一张卡收一个数据块并累加。走完 $N-1$ 步后，**每张卡上恰好有一个数据块，是全体 $N$ 张卡在该块上的完整求和结果**（其余块仍是局部和）。
2. **All-Gather 阶段**（$N-1$ 步）：把第一阶段"各自持有一块完整结果"的状态，通过同样的环形传递方式，让每张卡都拿到全部 $N$ 块的完整结果。

**通信量计算**：每一步，每张卡发送和接收的数据量都是 $S/N$（一个数据块的大小）。两个阶段各 $N-1$ 步，所以单卡总通信量：

$$\text{单卡总通信量} \approx \frac{2(N-1)}{N} \times S$$

当 $N$ 较大时，$\frac{2(N-1)}{N} \to 2$，即**单卡通信量收敛到约 $2S$，与卡数 $N$ 完全无关**——这就是"通信量与卡数无关"这句话的真实含义：不是完全不变（严格说是随 $N$ 增大趋近一个常数），而是不会随着卡数增多而线性增长，因此可以持续 scale 到成百上千张卡而不会让通信成为瓶颈的主导项（只要网络带宽本身足够）。

对照朴素做法（总管带宽随 $N$ 线性增长）就能看出 Ring All-Reduce 为什么是 DDP、乃至几乎所有分布式训练通信库（NCCL 的默认算法之一）的基石。

#### 深入 DDP 的其余核心机制

1. **梯度分桶（Gradient Bucketing）**：反向传播是从后往前逐层产生梯度的，DDP 不会等所有梯度都算完才通信，而是把梯度按大小分桶（默认约 25MB 一个桶），某个桶内的梯度全部就绪后立刻发起 All-Reduce，不用等整个反向结束。
2. **计算-通信重叠（Overlap）**：桶的 All-Reduce 与后续层（更靠前的层）的反向计算并行执行，用独立的 CUDA Stream 把通信过程"藏"在计算背后，这是 DDP 相比朴素 DP 吞吐大幅提升的关键，也是本文后面几乎所有并行策略反复出现的优化母题。
3. **`no_sync()` 上下文**：做梯度累积（Gradient Accumulation，用多个 micro-batch 模拟大 batch）时，中间的 micro-batch 步跳过 All-Reduce（用 `no_sync()` 包裹），只在最后一个 micro-batch 时才真正同步梯度，减少不必要的通信次数。
4. **静态图假设**：DDP 默认假设每次迭代的计算图结构不变（`find_unused_parameters=False` 时性能最好，因为它可以提前确定分桶方案）。动态子图/条件计算（某些 MoE 路由场景）会导致某些参数在某次迭代不参与计算，若不处理会让 DDP 在等待一个永远不会产生的梯度上死锁（hang）。

DDP 的局限很直接：**每卡都要放得下完整的参数 + 梯度 + 优化器状态**（即 0.1 节算出的 $16\Phi$ 字节），模型一旦超过单卡显存，就必须引入显存分片，这就是 ZeRO/FSDP 要解决的问题。

### 1.2 ZeRO（DeepSpeed）：把"复制"换成"分片"

ZeRO（Zero Redundancy Optimizer）的核心洞察：DDP 里每张卡的参数/梯度/优化器状态都是**完全冗余**复制的（$N$ 张卡存了 $N$ 份一模一样的东西），而模型状态在任意时刻真正需要"完整"存在的只是当前正在计算的那一层——ZeRO 把冗余部分分片到 $N$ 张卡上，需要时再临时聚合，用完即释放。

#### 三个 Stage 的显存与通信精确账本

设优化器状态系数 $K=12$（对应 0.1 节的 Adam $12\Phi$），模型状态总字节数为

$$4\Phi\ (\text{参数+梯度}) + K\Phi\ (\text{优化器状态}) = 16\Phi$$

数据并行度为 $N_d$：

* **ZeRO-1（只分片优化器状态）**：优化器状态从 $K\Phi$ 降到 $K\Phi/N_d$，其余不变。以 $N_d$ 较大为例，显存降幅可达约 **4 倍**。**通信量与 DDP（纯 All-Reduce）完全相同**——反向仍然算出完整梯度做 All-Reduce，只是更新参数时每卡只更新自己负责的分片，再 All-Gather 回完整参数（这次 All-Gather 的量相对全量梯度通信是小头，通常忽略不计或与优化器 step 频率摊薄）。
* **ZeRO-2（再分片梯度）**：在 ZeRO-1 基础上，梯度也不再要求每卡持有完整份，而是反向算出来后直接 **Reduce-Scatter**（而不是 All-Reduce）到对应分片。显存降幅可达约 **8 倍**。**通信量同样与 DDP 持平**——Reduce-Scatter + 后续更新完的 All-Gather，总通信量和一次 All-Reduce 是同一个量级（All-Reduce 本身在实现上就是 Reduce-Scatter + All-Gather 两阶段，见 1.1 节的 Ring All-Reduce 推导）。
* **ZeRO-3（再分片参数）**：每卡平时只保存参数的 $1/N_d$，前向/反向经过某一层前，先对该层做一次 **All-Gather** 拼出完整参数，用完立刻释放，只留自己的分片。显存降幅**随 $N_d$ 近乎线性**（理论上可以无限逼近"总显存/卡数"，让训练万亿参数模型成为可能）。代价是通信量比前两个 Stage **多约 50%（$1.5\times$ 于 DDP 基线）**——因为多了参数本身的 All-Gather（前向一次、反向一次），这是用通信换取几乎线性的显存下降，工程上认为是划算的。
* **ZeRO-Offload / ZeRO-Infinity**：进一步把优化器状态（Offload）甚至参数（Infinity）搬到 CPU 内存乃至 NVMe，用 PCIe/NVMe 带宽换显存容量，适合单机少卡也要跑大模型微调的场景，训练吞吐会明显下降，是"能跑起来"与"跑得快"之间的取舍，常见于资源受限的个人/小团队场景。
* **ZeRO++（进阶）**：微软后续工作，通过**权重量化**（通信前把 FP16 权重量化到 INT8 再传输、通信后再反量化）和**分层分区**（Hierarchical Partitioning，优先在节点内做通信、减少跨节点慢速链路的流量）等手段，在保持精度的同时把通信量在特定场景下降低约 4 倍，主要面向多机训练带宽受限（比如没有 InfiniBand，只有普通以太网）的场景。

#### worked example：7B 模型在 64 卡 DP 下，三个 Stage 各占多少显存

用 0.1 节的账本，7B 模型（$\Phi=7\times10^{9}$）模型状态总量 $16\Phi \approx 112\text{GB}$，其中优化器状态 $12\Phi \approx 84\text{GB}$、参数+梯度 $4\Phi \approx 28\text{GB}$。设数据并行度 $N_d = 64$：

| Stage | 优化器状态 | 梯度 | 参数 | 单卡模型状态显存 | 相对 DDP(112GB) 降幅 |
|---|---|---|---|---|---|
| DDP（无分片） | 84GB | 14GB | 14GB | 112GB | $1\times$（基线） |
| ZeRO-1 | $84/64 \approx 1.3\text{GB}$ | 14GB（不分片） | 14GB（不分片） | $\approx 29.3\text{GB}$ | $\approx 3.8\times$ |
| ZeRO-2 | $84/64 \approx 1.3\text{GB}$ | $14/64 \approx 0.22\text{GB}$ | 14GB（不分片） | $\approx 15.5\text{GB}$ | $\approx 7.2\times$ |
| ZeRO-3 | $84/64 \approx 1.3\text{GB}$ | $14/64 \approx 0.22\text{GB}$ | $14/64 \approx 0.22\text{GB}$ | $\approx 1.75\text{GB}$ | $\approx 64\times$（随 $N_d$ 近乎线性） |

可以直观看到：ZeRO-1/2 降幅很快就会随 $N_d$ 增大触顶（因为参数或梯度这两项不分片，始终占大头），到 $N_d=64$ 时 ZeRO-2 相对 ZeRO-1 的边际收益已经很有限；只有 ZeRO-3 会随卡数持续近乎线性下降，这也是为什么训练千亿参数级模型必须上 ZeRO-3（或等价的 FSDP），ZeRO-1/2 在这个规模下单卡显存依然装不下。代价是通信量：ZeRO-1/2 通信量与 DDP 基线打平，ZeRO-3 约 $1.5\times$——64 卡规模下这个额外的 50% 通信开销通常远小于"能不能装得下模型"这件事的重要性。

### 1.3 FSDP / FSDP2：PyTorch 原生的 ZeRO-3 实现

FSDP 理念上等价于 ZeRO-3，但实现路径不同：

* **FSDP1：FlatParameter 分片**。把一个被 wrap 的模块内所有参数打平（flatten）拼接成一个大的 1D tensor 再按 `torch.chunk` 切片存储。All-Gather/Reduce-Scatter 的调度粒度是"被 wrap 的模块"这一整块，颗粒度较粗；因为参数被打平失去了原始 shape 语义，与 `torch.compile`、部分参数冻结（如 LoRA 场景只训练 adapter、其余参数不参与梯度更新）等场景的兼容性较差，state_dict 的保存/加载也常需要额外的 All-Gather 才能拿到完整参数。
* **FSDP2（`fully_shard`，per-parameter sharding）**：改用 **DTensor**（PyTorch 分布式 Tensor 抽象）对**每个参数独立**沿 dim-0 分片（`torch.chunk(dim=0)`），不再打平拼接，保留参数原始 shape 语义。带来的直接好处：
  * **更好的组合性（composability）**：因为参数就是标准的 DTensor，FSDP2 可以和 TP（张量并行的 DTensor 切分）、其它并行方式自然组合，同一份代码基础设施能表达任意 N 维并行，这是 torchtitan 之类项目能用纯 PyTorch 原生 API 拼出 3D/4D 并行的基础；
  * **与 `torch.compile` 更兼容**：不需要在图里处理 flatten/unflatten 这类额外操作；
  * **放宽了冻结参数的限制**：可以对同一模型的不同参数子集独立决定是否分片、是否参与训练（LoRA/QLoRA 微调场景中大量参数被冻结，FSDP2 处理得更干净）；
  * **通信更省**：sharded state_dict 可以直接用 DTensor 表示并落盘，无需先做一次 All-Gather 拼出完整参数再保存（FSDP1 常需要），加快 checkpoint 保存速度。
* **通信时序（前向/反向都遵循同一模式）**：进入某层前，对该层参数做 **All-Gather**（同时会 prefetch 下一层的 All-Gather，让通信和当前层计算重叠）→ 执行该层前向/反向计算 → 计算完立刻释放非本分片部分的参数，只保留自己那一份 → 反向阶段梯度算出来后做 **Reduce-Scatter** 分片保存。这个"用时聚合、算完释放"的模式是理解 ZeRO-3/FSDP 显存曲线为什么能做到"显存占用只与分片后的状态相关，与总层数无关（因为不会同时展开所有层的完整参数）"的关键。

### 1.4 三者怎么选

| 维度 | DDP | DeepSpeed ZeRO | PyTorch FSDP/FSDP2 |
|---|---|---|---|
| 显存分片粒度 | 不分片（$16\Phi$ 全量复制） | Stage 1/2/3 可选，对应 $4\times$/$8\times$/近线性显存降幅 | 等价 ZeRO-3，per-parameter 分片（FSDP2） |
| 通信量相对 DDP | 基线 | Stage1/2 与 DDP 持平，Stage3 约 $1.5\times$ | 约 $1.5\times$（同 ZeRO-3） |
| 生态位 | 模型能塞进单卡时的默认选择 | 与 Megatron 深度整合（3D 并行 + ZeRO），Offload 能力最强（ZeRO-Infinity），RLHF 生态成熟（DeepSpeed-Chat/OpenRLHF） | PyTorch 原生，新一代预训练/后训练框架（torchtitan、verl 等）常用后端之一 |
| 与其它并行组合 | 需搭配 Megatron-style TP/PP 手动组合 | 官方支持 ZeRO + TP/PP 混合（3D 并行） | FSDP2 基于 DTensor 天然可与 TP、CP 组合 |
| 易用性 | 最简单，一行 wrap | 需要写 config json，概念较多但文档成熟、案例多 | API 简洁，FSDP1 的 wrap policy 调试有门槛，FSDP2 已大幅简化 |
| 典型场景 | 中小模型全量训练/微调 | 超大模型预训练、显存极度紧张场景（CPU/NVMe offload） | HuggingFace/PyTorch 原生生态微调与预训练，RL 训练框架（verl 等）常用训练后端 |

### 1.5 通信库内部机制：NCCL 到底怎么把 All-Reduce 铺到硬件拓扑上

前面所有并行策略的通信开销分析，都默认"All-Reduce/All-Gather 就是把 1.1 节推导的 Ring 算法跑一遍"，但实际的 NCCL（NVIDIA Collective Communications Library）会根据集群规模和拓扑动态选择算法，理解这层才能看懂 Nsight Systems 里的通信 timeline 为什么长这样。

* **Ring 算法**（1.1 节推导的就是它）：把参与通信的所有 GPU 连成一个环，每一步所有链路都在满负荷工作，是**带宽最优**的方案（单位时间内传输的总数据量最大），适合中小规模集群——因为环越长，Reduce-Scatter+All-Gather 的总步数 $2(N-1)$ 也越长，每一步都有基础的启动延迟（latency），大规模集群下这些延迟累加起来会超过节省的带宽收益。
* **Tree 算法**：把 GPU 组织成二叉树结构，每一轮通信分"规约（Reduce）阶段"和"广播（Broadcast）阶段"两步走完（而不是 Ring 的 $2(N-1)$ 步）。步数是 $O(\log N)$ 量级，**延迟更优**，代价是树的不同链路负载不均衡（靠近根节点的链路承担的流量明显更多），带宽利用率不如 Ring。NCCL 的经验法则是：**集群规模超过约 32 个节点后，Tree 的低延迟优势开始超过 Ring 的带宽均匀优势**，NCCL 会自动切换算法（也可以手动配置）。
* **PXN（PCIe × NVLink）**：单机内多张 GPU 可能只有部分卡直连网卡（NIC），PXN 让 NCCL 先利用节点内的 NVLink 把要发往远端的数据在本地聚合/转发到"离目标网卡最近"的那张 GPU，再统一通过该网卡发出——本质是用 NVLink 的高带宽做"最后一公里转发"，让一个节点上的多张网卡都能被利用起来，节点间有效带宽可以随节点内网卡数近乎倍增（比如 4 张网卡理论上可提升到 4 倍跨节点带宽）。
* **SHARP / NVLS（NVLink SHARP，在网计算）**：更进一步，不再是"数据传到某处再规约"，而是让**交换机本身**参与规约计算——IB 交换机（SHARP）或 NVSwitch（NVLS）在数据流经的路上就地完成加法，数据不需要真正传到某张 GPU 上再算，减少了一次"传输+计算"变成了"边传边算"，可以显著降低 All-Reduce 的有效延迟和带宽占用，是目前超大规模集群（数千卡级）压榨通信性能的关键硬件特性，也是 Infra.md 里提到的 IB Rail-optimized 拓扑设计要充分利用的能力。
* **对训练系统设计的实际含义**：这解释了为什么 TP 必须限制在单机 NVLink 域内——TP 每层 4 次 All-Reduce（2.1 节），且这些 All-Reduce 处于前向/反向的关键路径上（不能像 DDP 梯度同步那样靠 overlap 完全藏起来，因为下一层的计算依赖这次 All-Reduce 的结果），一旦 TP 跨机走 IB/以太网，即使有 Tree/SHARP 加持，延迟仍然会比 NVLink 高一到两个数量级，直接拖慢每一层的前向/反向。

## 2. Megatron-LM 与模型并行：把单层也切开

数据并行的分片再激进，切的始终是"不同数据副本间"的冗余；当**单层参数本身**就放不进单卡（如百亿/千亿参数模型的一个 Attention/MLP 层），就需要模型并行——把一层内部的计算切开分布到多卡。

### 2.1 张量并行（TP）：矩阵乘法怎么被拆开

以 Transformer 的 MLP 层为例，其计算是

$$Y = \text{GeLU}(XA)B$$

其中 $X$ 是输入激活（形状 $[\text{batch}\times\text{seq}, \text{hidden}]$），$A$ 是升维矩阵（$[\text{hidden}, 4\text{hidden}]$），$B$ 是降维矩阵（$[4\text{hidden}, \text{hidden}]$）。

* **列并行（Column Parallel）切 $A$**：把 $A$ 按列切成 $N$ 份 $[A_1, A_2, \ldots, A_N]$，每张卡只存一份 $A_i$（形状 $[\text{hidden}, 4\text{hidden}/N]$）。每卡各自算出 $XA_i$（一个部分列的结果），由于 GeLU 是**逐元素**运算，可以直接对每张卡的部分结果独立做 GeLU，**不需要通信**。
* **行并行（Row Parallel）切 $B$**：把 $B$ 按行切成 $N$ 份，恰好对应上一步每张卡持有的中间结果的列数。每卡用自己的 $\text{GeLU}(XA_i)$ 乘以 $B_i$ 得到一个部分和 $Y_i$（形状与最终输出相同，但只是 $N$ 份分量之一）。最后需要一次 **All-Reduce** 把 $N$ 张卡的 $Y_i$ 求和，得到完整的 $Y = \sum_{i=1}^{N} Y_i$。
* **Attention 层类似处理**：多头注意力天然可以按 head 维度切分（每张卡负责一部分 head），QKV 投影矩阵按列切、输出投影矩阵按行切，逻辑与 MLP 完全对称，最后同样是一次 All-Reduce 收尾。

**通信触发点精确统计**：一个标准 Transformer block（Attention + MLP）里，Attention 结束一次 All-Reduce、MLP 结束一次 All-Reduce，前向共 2 次；反向传播里对称地也需要 2 次 All-Reduce（把上游传回来的梯度在列并行的切分维度上做规约）。也就是说**每层前向 2 次、反向 2 次 All-Reduce**，且 TP size 越大，每次 All-Reduce 的参与方越多、每层的通信开销占比越高。这正是 TP 通信开销的来源，因此 **TP 必须在高带宽域内做**（同机 NVLink 域内，带宽可达数百 GB/s 到 TB/s 级别），跨机做 TP（走 InfiniBand/以太网，带宽通常只有 NVLink 的十分之一到几十分之一）会让通信严重拖累计算，因此 TP size 一般不超过单机 GPU 数（常见 8）。

* **Sequence Parallel（SP）**：TP 已经把 Attention/MLP 内部切开了，但 LayerNorm、Dropout 这类**逐 token 独立**的操作在纯 TP 里仍然是每张卡都重复计算和存储完整序列长度的激活，造成显存浪费（因为这些操作不涉及 hidden 维度的矩阵乘，无法用 TP 的切分方式处理）。SP 把这部分操作沿**序列维度**也切分到 TP 组内各卡，每卡只处理 $\text{seq\_len}/N$ 长度的 token；在进入需要完整序列信息的 Attention/MLP 之前，用一次 **All-Gather** 把序列维度重新拼回完整长度，退出时再用 **Reduce-Scatter** 切回序列并行状态。巧妙之处在于，这些额外的 All-Gather/Reduce-Scatter **恰好可以替换掉原本 TP 里的部分 All-Reduce**（All-Reduce 在数学上等价于 Reduce-Scatter + All-Gather，SP 只是把这两个子操作错开位置插入），因此 SP 相比纯 TP **几乎不增加额外通信量**，却能把 LayerNorm/Dropout 相关的激活值显存降低到 $1/N$，现在工业界默认 TP 搭配 SP 使用。

#### worked example：TP 一次 All-Reduce 到底传多少字节

以 $\text{hidden}=4096$、$\text{batch}\times\text{seq}=8192$（比如 batch=2，seq=4096）、$\text{TP\_size}=8$ 为例，MLP 层输出 $Y$（All-Reduce 前每卡持有的部分和 $Y_i$）的形状是 $[8192, 4096]$，FP16 下单卡这次要 All-Reduce 的数据量：

$$8192 \times 4096 \times 2\text{字节} \approx 64\text{MB}$$

按 1.1 节 Ring All-Reduce 的通信量公式，单卡实际收发总量：

$$\frac{2\times(8-1)}{8}\times 64\text{MB} \approx 112\text{MB}$$

一个 block 前向要做 2 次这样的 All-Reduce（Attention 一次、MLP 一次），反向再来 2 次，一层就是约 $4 \times 112\text{MB} \approx 448\text{MB}$ 的单卡通信量。如果模型有 80 层，一次前向+反向单卡通信总量粗略估算可达 **35GB 量级**——这就是为什么 TP 通信必须挂在 NVLink（数百 GB/s 到 TB/s 带宽）上：换算下来哪怕是 900GB/s 的 NVLink，仅这部分通信也要几十毫秒，如果换成几十 GB/s 的跨机网络，会直接拖垮单层前反向的整体耗时。这也说明了为什么 TP_size 不能无脑调大——TP_size 越大，每次 All-Reduce 的参与方越多（虽然 Ring 通信量本身随 $N$ 增大趋近常数，但启动延迟部分是随 $N$ 增长的），且需要占用的 NVLink 域也越大。

### 2.2 流水线并行（PP）：把模型按层切开，及 bubble 问题的数学

* **核心思路**：把模型按层切成 $P$ 个 stage，分布到 $P$ 组卡上，像工厂流水线一样，让不同 micro-batch 在不同 stage 同时被处理（stage 1 处理 micro-batch 2 的同时，stage 2 在处理 micro-batch 1）。

#### 深入：为什么会有 Bubble，比例怎么算

假设一个 micro-batch 的前向耗时和反向耗时都是 1 个时间单位（反向通常记为 2 个单位，这里为了直觉简化按 1:1），流水线有 $P$ 个 stage，一次训练迭代内有 $M$ 个 micro-batch。

**朴素流水线（GPipe）的调度**：先让所有 $M$ 个 micro-batch 依次流过 $P$ 个 stage 完成前向（这时候第 1 个 stage 早就闲下来了，因为它的前向任务很快做完，但要等所有 micro-batch 都进入流水线），再让它们依次做反向。画出时间-stage 的方格图会发现，流水线的"启动"（第一个 micro-batch 要走满 $P$ 个 stage 才能开始产出结果）和"排空"（最后一个 micro-batch 走完全部 stage）阶段，有些 stage 是空闲的，这段空闲时间就是 **Bubble**。

推导：完整跑完 $M$ 个 micro-batch 的前向+反向，理想情况下（无 bubble）总耗时应为 $2M$（$M$ 个 micro-batch，每个前向+反向各 1 单位，且所有 stage 完全并行工作，只有一个"稳态"耗时）。但实际总耗时是 $2M + 2(P-1)$（多出的 $2(P-1)$ 就是流水线启动和排空阶段的空闲时间，等于 $P-1$ 个 stage 的空闲乘以前向+反向各占一份）。**Bubble 比例**：

$$\text{Bubble 比例} = \frac{\text{空闲时间}}{\text{理想总时间}} \approx \frac{P-1}{M}$$

当 $M$ 远大于 $P$ 时，这个比例趋近于 0，即 micro-batch 数越多，bubble 占比越小——这也是为什么要把 batch 切成足够多的 micro-batch 而不是越少越好。

**worked example**：$P=4$（4 个 stage），$M=8$（8 个 micro-batch）。Bubble 比例：

$$\frac{4-1}{8} = 37.5\%$$

意味着理论上超过三分之一的 GPU-时间在空转。用文字画一下 4 个 stage 的时间线（每格代表 1 个时间单位的前向 F 或反向 B，数字是 micro-batch 编号）：stage 0 从 $t=0$ 就开始做 F1、F2...F8，然后做 B1...B8；stage 3（最后一个 stage）要等 F1 依次穿过 stage 0/1/2 才能在 $t=3$ 开始做 F1，且它做完 F1 后立刻能做 B1（因为它是最后一个 stage，没有下游依赖），所以 stage 3 的启动延迟是 3 个时间单位，stage 0 的排空延迟同样是 3 个单位（等 B8 从 stage 3 一路传回来）——这两段"陪跑"时间就是 $2(P-1)=6$ 个单位的由来，除以理想总时间 $2M=16$，算出来正好是 37.5%。如果把 $M$ 提到 32（同样 $P=4$），bubble 比例降到 $\frac{4-1}{32} \approx 9.4\%$，直观验证了"micro-batch 数越多、bubble 占比越小"。这也是为什么 PP_size 定下来之后，还需要足够大的全局 batch size 去切出足够多的 micro-batch，否则 PP 的效率会很难看。

* **1F1B（One-Forward-One-Backward）**：Megatron 的标准调度，不再是"全部前向完再全部反向"，而是让每个 stage 一旦有梯度可以反向，就尽早开始反向（而不是等所有 micro-batch 都 forward 完）。这不改变 bubble 比例（数学上仍是 $\frac{P-1}{M}$），但**峰值显存大幅降低**：GPipe 需要同时缓存所有 $M$ 个 micro-batch 的激活值（等它们全部前向完才能开始反向），1F1B 因为反向紧跟着前向及时释放，同一时刻只需缓存 $P$ 个左右 micro-batch 的激活，这是 1F1B 成为工业界默认方案的核心原因（bubble 没变但显存友好得多）。
* **Interleaved 1F1B（虚拟流水线）**：让每张卡负责多个**不连续**的 stage 段（而不是连续的一段层，比如卡 0 负责第 1 层和第 $P+1$ 层），这样"启动+排空"阶段每个 stage 的粒度变小，bubble 比例可以进一步降低（近似降低为 $\frac{P-1}{M\times v}$，$v$ 是每卡负责的虚拟 stage 数），代价是每个 micro-batch 要在同一张卡的不同虚拟 stage 之间多次进出，通信/调度次数增加。
* **Zero Bubble PP（清华 2024，ZB-H1/ZB-H2）**：核心洞察是反向传播其实包含两个相对独立的计算——**对输入的梯度**（用于继续往前传播，即 B，Backward-Input）和**对权重的梯度**（用于更新参数，即 W，Backward-Weight）。传统实现把这两部分捆绑在一起当作一个不可分割的"反向"操作调度，但实际上 W 部分算完可以立刻丢给优化器，不影响流水线的前后依赖关系，因此可以被**延后到更灵活的时间点插入**，填补原本的 bubble 空隙。**ZB-H1** 沿用类似 1F1B 的显存占用但通过拆分 B/W 缩小 bubble；**ZB-H2** 通过进一步延后 W 的调度实现（近似）零 bubble，代价是更高的显存占用，并需要引入一次额外的"校验-回滚"（validation and rollback）步骤来处理因调度乱序可能带来的数值误差，弥补跳过标准同步带来的正确性风险。这是目前 PP 调度层面最前沿的工作方向。
* **显存权衡总结**：PP 不切参数本身（每个 stage 完整持有自己那部分层的参数、梯度、优化器状态），主要收益是**把总参数量摊到多张卡**（每卡只需装下 $1/P$ 的层），副作用是引入 bubble（算力浪费）以及跨 stage 传递激活值/梯度的 P2P 通信延迟。

### 2.3 3D 并行：DP × TP × PP 的组合逻辑

Megatron-LM 训练超大模型的标准姿势是三者组合，划分逻辑遵循"通信域从小到大匹配硬件拓扑"的原则：

1. **TP** 放在单机内 NVLink 域（通信最频繁——每层 4 次 All-Reduce、对带宽最敏感）；
2. **PP** 跨机（每次 P2P 传输的是激活值/梯度，量相对小、频率相对低，能容忍稍高的跨机延迟）；
3. **DP**（常配合 ZeRO-1/2 分片优化器/梯度）放在最外层，跨 PP×TP 组之间同步梯度，通信频率最低（每个 step 一次 All-Reduce 或 Reduce-Scatter）。

总卡数

$$N_{\text{total}} = \text{DP\_size} \times \text{TP\_size} \times \text{PP\_size}$$

调参的核心思路：先根据单层参数量确定 TP_size（刚好塞得下一层即可，不多切，因为 TP 通信开销随 size 增大而增加）；再根据总参数量和 TP 已经省出的显存确定 PP_size（PP_size 越大，bubble 比例 $\frac{P-1}{M}$ 越高，需要用更多 micro-batch 摊薄）；剩下的卡数全部用作 DP 提升整体吞吐（DP 的 Ring All-Reduce 通信量与卡数无关，扩展性最好，是"用剩下的卡"的默认选择）。

## 3. MoE 并行：专家并行（EP）

MoE（Mixture-of-Experts）在 DeepSeek-V3/R1 之后成为大模型训练的主流架构，引入了第四种并行维度。

### 3.1 路由机制与 All-to-All 通信

* **Router（门控网络）的精确计算**：对每个 token 的隐藏状态 $h$（维度 $[\text{hidden}]$），经过一个线性层

$$g = h \cdot W_{\text{gate}}$$

（$W_{\text{gate}}$ 形状 $[\text{hidden}, \text{num\_experts}]$）得到每个 expert 的打分 logits，再过 **softmax**：

$$p_i = \frac{\exp(g_i)}{\sum_j \exp(g_j)}$$

（DeepSeek 系模型也常用 sigmoid 代替 softmax）得到路由概率分布，取 **Top-$K$**（常见 $K=2$，DeepSeek 风格是更大的 $K$ 但配合"细粒度专家"让单个 expert 更小）得分最高的几个 expert，token 的最终输出是这 $K$ 个被选中 expert 各自输出的**加权和**（权重就是对应的路由概率，通常重新归一化让 $K$ 个权重加起来等于 1）。
* **容量因子（Capacity Factor）**：由于路由结果是动态的，理论上某个 expert 可能被远超"平均分配量"的 token 选中。为了让批处理里每个 expert 的计算规模保持规整（便于做批量矩阵乘，也便于 All-to-All 通信提前分配好固定大小的缓冲区），系统会给每个 expert 设一个容量上限：

$$\text{capacity} = \text{capacity\_factor} \times \frac{\text{总 token 数}}{\text{num\_experts}}$$

$\text{capacity\_factor}$ 取 $1.0$ 表示"恰好按平均分配量"，实践中常设为 $1.25$ 甚至更高，为路由不均匀预留余量；超出容量的 token 在早期实现中会被丢弃（对应下文的 Drop-less 问题）。
* **Expert Parallelism（EP）**：把不同 expert 分布到不同卡上（而不是像 TP 那样把同一个 expert 内部的矩阵乘再切开，虽然两者也可以叠加）。一个 token 经过 router 决策后，要被发送到它所选中的 expert 所在的卡——这个"发送"用的就是 **All-to-All** 通信原语：每张卡把自己负责的一批 token 按照它们各自的路由目标，分发给对应的 expert 所在卡（dispatch），expert 算完后再用一次 All-to-All 把结果传回 token 原本所在的卡（combine）。
* **All-to-All 是新的通信瓶颈**：不同于 TP/DP 的 All-Reduce（每次通信量固定可预测），All-to-All 的通信量取决于路由结果（哪些 token 去了哪些卡），负载不均衡时（某些热门 expert 被大量 token 选中）容易出现长尾——某张卡等待另一张卡处理远超平均量的 token，拖慢整个 step。粗略估算：设 $\text{EP\_size}=E$ 张卡，每卡本地 token 数 $T$，每个 token 隐藏维度 $\text{hidden}$，Top-$K$ 路由，理想（完全均匀）情况下 dispatch 阶段单卡要发出的数据量约为：

$$T \times K \times \text{hidden} \times \text{字节数} \times \frac{E-1}{E}$$

（每个 token 平均要发往 $K$ 个不同 expert，且约 $\frac{E-1}{E}$ 的比例是发往"别的卡"而非本地），combine 阶段做一次同等量级的反向传输——这个量级和 Ring All-Reduce 里"单卡通信量趋近常数"的良性特性不同，**All-to-All 的通信量会随 EP_size 和 Top-K 增大而实打实地增长**，这也是为什么 DeepEP 这类专门优化的通信库价值很大：同样的路由决策，通信实现效率的差异直接决定了 EP 能扩展到多少张卡而不被通信拖垮。

### 3.2 DeepEP：目前性能最好的 MoE 通信库

DeepSeek 开源的 **DeepEP** 是专门为 MoE dispatch/combine 场景优化的 All-to-All 通信库，核心特性（已核实）：

* 提供高吞吐、低延迟的 all-to-all GPU kernel，同时支持节点内（NVLink）和节点间（RDMA）两种拓扑；
* 针对 DeepSeek-V3 论文提出的 **group-limited gating**（分组限制路由，即限制每个 token 最多路由到几个"组"内的 expert，减少跨节点通信范围）专门优化了一套 kernel，支持"从 NVLink 域转发到 RDMA 域"这种非对称带宽转发场景；
* 支持 **FP8** 等低精度通信，进一步压缩传输数据量；
* 针对推理 decode 阶段的延迟敏感场景，提供纯 RDMA 实现的低延迟 kernel，并引入一种基于 hook 的通信-计算重叠方法，**不占用任何 SM（流多处理器）资源**做通信调度，把通信开销压到最低；
* 所有 kernel 通过轻量级 JIT（Just-In-Time）在运行时编译，安装时无需预编译 CUDA。

### 3.3 负载均衡

* **Auxiliary Loss（辅助负载均衡损失）**：在主任务 loss 之外加一项惩罚项，鼓励 router 把 token 均匀分配给各个 expert（避免"赢家通吃"，某几个 expert 累积大量 token 而其余 expert 很少被用到）。缺点是这个辅助 loss 会和主任务目标产生一定冲突，系数没调好会伤害模型效果。
* **DeepSeek-V3 的无辅助损失负载均衡**：不再用一个额外的 loss 项去"软性引导"，而是给每个 expert 维护一个**动态偏置（bias）**，如果某个 expert 最近被路由到的 token 偏多，就调低它的偏置（降低下一轮被选中的倾向），偏少则调高，用一种类似 PID 反馈控制的方式直接调节路由决策本身，而不干扰主 loss 的梯度，是 V3 相比早期 MoE 工作在负载均衡机制上的关键改进。
* **Drop-less MoE**：早期 MoE 实现为了保证通信/计算的规整性，会给每个 expert 设一个"容量"（capacity），超出容量的 token 直接被丢弃（不参与该次 expert 计算，直接跳过 FFN 或走残差连接），影响这些溢出 token 的训练质量。Drop-less 的设计目标是让所有 token 都不被丢弃，通常需要更精细的动态容量分配或后处理机制。
* **细粒度专家（Fine-grained Expert）**：DeepSeek 风格把每个 expert 拆得更小、数量更多（例如上百个 routed expert 加若干 shared expert 常驻处理所有 token 的通用信息），配合更大的 Top-K，提升专家专精度和路由组合的灵活性，代价是 All-to-All 通信更碎片化（要和更多不同的卡交换更小份的数据）。
* EP 通常与其它并行方式组合：常见配置是模型的 Attention 部分用 TP（Attention 参数量相对小，切分收益有限但仍需要），MoE FFN 部分用 EP（FFN 部分是参数量的绝对大头），两者共享底层的 DP 维度。

## 4. DeepSpeed 生态全景

DeepSpeed 不只是 ZeRO，是微软的一整套训练+推理+压缩工具箱，容易被低估的部分：

### 4.1 DeepSpeed-Ulysses：另一条长序列并行路线

面向长序列训练的序列并行方案，和 Megatron 的 SP（沿序列维切分 LayerNorm/Dropout，前面已讲）思路不同——Ulysses 是一种**更彻底**的序列切分：

* 输入序列在进入 Attention **之前**，就已经按序列维度切分到各卡（每卡只有 $\text{seq\_len}/N$ 长度的一段）；
* 在 Attention 计算**之前**，先做一次 **All-to-All**，把数据从"序列切分"转换成"注意力头（head）切分"——每张卡从只持有部分序列、全部 head，变成持有全部序列、部分 head；
* 这样每张卡就能独立完整地计算它负责的那些 head 上的完整 Attention（不需要像 Ring Attention 那样在多卡间逐块传递 KV 分块），算完后再用一次 All-to-All 把结果转换回"序列切分"状态，继续后续的 FFN 等逐 token 操作。
* **关键优势**：All-to-All 的通信量只与模型大小（head 数、hidden 维度）和卡数相关，**与序列长度无关**（因为传输的是固定的 head/hidden 维度数据，只是重新排布，不随 seq_len 增长而增长通信量本身的系数），这是它区别于 Ring Attention（通信量随参与卡数和序列分块数变化更复杂）的核心系统特性，是实现长上下文训练的另一条重要路线（对照 Infra.md 中提到的 Ring Attention / Context Parallelism）。

### 4.2 其它组件

* **3D 并行支持**：DeepSpeed 可以和 Megatron 的 TP/PP 结合（业内俗称"Megatron-DeepSpeed"），ZeRO 只作用于最外层的 DP 维度，TP/PP 仍按 Megatron 的方式处理。
* **DeepSpeed-MoE**：专家并行 + ZeRO 的组合实现，是早于 DeepEP 的另一条 MoE 系统化路线，两者可以视为业界在同一问题（高效 MoE 训练）上的不同方案。
* **DeepSpeed-Chat / DeepSpeed-RLHF**：把 SFT → Reward Model → PPO 三阶段封装成一体化训练流程，是较早的开源 RLHF 系统实现（详见第 7 章，OpenRLHF 等后续框架的很多设计思路受其启发）。
* **DeepSpeed-Inference / ZeRO-Inference**：DeepSpeed 自身也有推理优化路径（kernel 融合 + 张量并行 + 量化），但目前工业界推理服务化场景已被 vLLM/SGLang/TensorRT-LLM 主导（见第 6 章），DeepSpeed-Inference 更多用于与训练框架无缝衔接、不想引入额外推理引擎依赖的场景。

## 5. PyTorch 原生技术栈：torchtitan 与组合式并行

除了 Megatron-LM 和 DeepSpeed 这两个"重框架"，近两年出现了以 **组合优先（composability）** 为设计目标的原生方案：

* **torchtitan**：PyTorch 团队官方的预训练参考实现，展示如何用 **FSDP2（DTensor）+ TP（DTensor）+ PP + Context Parallel** 任意组合出 N 维并行，且都用 PyTorch 原生 API（无需 Megatron 那样的自定义 CUDA/C++ 扩展），是理解"并行策略应该是可组合的正交维度，而不是框架里写死的固定套餐"这一设计理念的最佳阅读材料。因为 FSDP2 和 TP 都基于同一套 DTensor 抽象，两者组合时不需要额外的胶水代码。
* **veScale（字节）**：思路类似，强调**自动并行化**——用户写单卡视角的模型代码，框架自动分析并插入切分策略，进一步降低多维并行的手写代码负担。
* 这类框架代表的趋势：**并行策略正从"框架里的固定组合"（Megatron 早期把 TP/PP/DP 三件套的实现耦合写死在代码里）走向"独立可插拔的原语"（在 DTensor 之上按需任意组合任意维度）**，长期看会持续降低多维并行的工程门槛，也是 verl 等新一代训练框架选择 FSDP 而非只支持 Megatron 的原因之一（组合灵活性优先）。

## 6. 推理系统与服务化深入

Infra.md 已经讲了 Prefill/Decode 差异、PagedAttention/RadixAttention 的动机、批处理范式演进，这里把关键数字算清楚、把两个最主流开源推理引擎的**系统架构**完整拆开。

### 6.1 Prefill 与 Decode：用数字说话

* **Prefill**：输入一个长度为 $L$ 的 prompt，一次前向就要算完 $L$ 个 token 的所有层计算，本质是一次"大矩阵乘大矩阵"（$[L, \text{hidden}] \times [\text{hidden}, \text{hidden}]$ 量级），FLOPs 随 $L$ 近似线性增长，而这次前向只需要读取一遍模型权重（$[\text{hidden}, \text{hidden}]$ 量级的数据量），因此**算术强度（FLOPs / 字节数）随 $L$ 增大而增大**——$L$ 越长，Prefill 越接近 compute-bound，越能吃满 GPU 算力（这也是为什么长 prompt 的首 token 延迟主要取决于算力而非带宽）。
* **Decode**：每一步只生成 1 个新 token，本质是"一个 token 的激活向量（$[1, \text{hidden}]$）乘权重矩阵"，这是一次**矩阵向量乘（GEMV）**，FLOPs 很小，但仍然要把整层权重、以及**该请求截至目前全部历史 token 的 KV Cache** 都从显存读一遍。算术强度极低（大量字节搬运、极少计算），是典型的 **memory-bound**，瓶颈是显存带宽而不是算力——这解释了为什么单独跑 decode 时 GPU 算力利用率往往只有个位数到十几个百分点。
* 这个本质差异直接导出了两个系统设计后果：（1）Prefill 和 Decode 混在同一批请求里调度会互相拖累（长 prefill 的大矩阵乘会独占 GPU 一段时间，期间正在 decode 的请求全部被阻塞，拉高 TPOT）；（2）**Continuous Batching 对 Decode 阶段收益巨大**——因为 decode 本身算力用不满，把多个请求的 decode 步"拼"成一个 batch 一起算，可以用同一次权重读取服务更多 token，显著提升算术强度和整体吞吐（这也是为什么 batch size 是 decode 吞吐最重要的旋钮）。

### 6.2 KV Cache：大小怎么算、GQA/MQA 怎么帮忙

标准 Multi-Head Attention 的 KV Cache 大小（每个请求，FP16 精度）：

$$\text{KV Cache 字节数} = 2 \times \text{num\_layers} \times \text{num\_kv\_heads} \times \text{head\_dim} \times \text{seq\_len} \times 2$$

（第一个 2 对应 K 和 V 两份，最后一个 2 是 FP16 字节数）。以一个 32 层、32 个 KV head、$\text{head\_dim}=128$ 的 7B 级模型为例，序列长度 4096 时：

$$2\times32\times32\times128\times4096\times2 \approx 2.1\text{GB}$$

**单个请求的 KV Cache 就有 GB 级**，这还只是一个请求，高并发场景下 KV Cache 是显存里除模型权重外最大的开销，也是"能同时服务多少并发请求"的直接决定因素。

* **GQA（Grouped-Query Attention）/ MQA（Multi-Query Attention）**：注意到上面公式里 $\text{num\_kv\_heads}$ 这一项——标准 MHA 中 $\text{num\_kv\_heads} = \text{num\_query\_heads}$，而 GQA 让多个 query head 共享同一组 K/V head（比如 32 个 query head 只对应 8 组 K/V，压缩比 $4\times$），MQA 是极端情况（所有 query head 共享 1 组 K/V）。这直接让 KV Cache 大小按 $\text{num\_kv\_heads}$ 的压缩比例线性下降，是几乎所有现代开源模型的标配设计，本质上是在 Decode 阶段"用极少的精度损失换显存带宽"（前面说过 Decode 是 memory-bound，KV Cache 越小，带宽压力越小，吞吐越高）。
* **KV Cache 量化**：把 FP16 的 KV Cache 进一步压缩到 FP8/INT4，进一步降低 decode 阶段的带宽需求，代价是精度损失（KV Cache 量化通常比权重量化更敏感，需要更精细的 per-token/per-channel 量化方案）。
* **KV Cache offload**：显存放不下时把暂时不用的 KV Cache 换出到 CPU 内存甚至 NVMe，多级缓存应对超长上下文和海量并发，代价是换入换出的延迟。

### 6.3 vLLM 架构解剖

vLLM 的核心贡献是把操作系统的虚拟内存管理思想搬到了 KV Cache 上：

* **PagedAttention**：KV Cache 不再要求逻辑上连续存储，而是按固定大小的 **block**（常见默认 block size 为 16 个 token）分配，通过 **block table** 做逻辑地址到物理显存块的映射（直接类比 OS 的页表机制）。带来两个直接收益：
  1. **消除显存碎片**：不需要为每个请求预先分配"最大可能长度"的连续显存（传统实现常见的显存浪费方式），而是按实际生成进度动态分配 block，接近零浪费；
  2. **天然支持共享**：多个请求（如同一 prompt 的多个采样分支，或共享 system prompt 的不同请求）可以让各自的 block table 指向同一物理 block，配合**写时复制（Copy-on-Write）**——只有当某个共享 block 需要被某个请求独立修改时，才为它复制一份新 block，其余情况下持续共享同一份物理显存，最大化利用率。
* **系统组件**：
  * **Scheduler**：决定每个 step 哪些请求参与本轮计算（新请求何时加入、哪些请求需要因显存不足被 preempt/swap 出去），是 Continuous Batching 的调度大脑；
  * **BlockManager**：维护物理 block 的分配、引用计数（支持上面说的共享机制）、驱逐策略（显存不够时选择把哪些请求的 KV Cache swap 到 CPU 或直接丢弃后续需要时重新计算，即 recompute）。**swap 还是 recompute 怎么选**：本质是比较两种代价——swap 的代价是"把 KV Cache 搬到 CPU 内存、需要时再搬回来"这一去一回的 PCIe 传输时间，与 KV Cache 大小（6.2 节公式）成正比；recompute 的代价是"重新对这个请求已生成的部分做一次 Prefill"，与已生成 token 数乘以模型算力开销成正比。当已生成序列较短时，重算比搬运数据更划算（这也是为什么被抢占的请求通常是刚开始生成不久、KV Cache 还不算大的那些——被抢占的代价小，调度器倾向优先抢占它们），vLLM 的调度器会依据这个成本比较动态决定，而不是固定用其中一种策略；
  * **Worker/ModelExecutor**：实际执行模型前向的进程（TP/PP 场景下有多个 worker 分布在不同卡），通过 NCCL 通信协调；
  * **Sampler**：处理 logits → token 的采样逻辑（temperature/top-p/top-k/beam search 等），且支持同一个 batch 内不同请求使用完全不同的采样参数（这是 continuous batching 场景下的一个不小的工程细节——不同请求的采样策略互不干扰）。
* **Continuous Batching（In-flight Batching）**：不像传统静态 batching 要等一整批请求全部生成完才能换下一批，vLLM 每个 decode step 结束后立刻检查：已完成的请求立刻出批腾出显存，队列里等待的新请求（做完一次 prefill 后）随时可以插入继续跟着 batch 一起做 decode，GPU 利用率相比静态 batching 有数量级提升，是现代推理引擎的标配设计。

### 6.4 SGLang 架构解剖

SGLang 从"如何让 LLM 程序（多轮对话、Agent、结构化生成）更快"出发，核心创新在缓存复用和调度器设计：

* **RadixAttention**：把所有历史请求的 KV Cache 组织成一棵**基数树（Radix Tree）**，树上每条边代表一段 token 序列对应的 KV Cache 块。任何新请求进来，先在树上做最长前缀匹配，命中的部分直接复用已经算好的 KV Cache，无需重新计算这部分的前向。相比 vLLM 早期需要用户显式声明共享前缀的 Prefix Caching，RadixAttention **自动**发现所有可能的前缀共享关系，对多轮对话（每轮都和历史高度重叠）、few-shot 提示（同一批 examples 反复出现）、树搜索类生成（如 Tree-of-Thought，同一节点下多个分支共享前缀）、Agent 场景（大量重叠的 system prompt/工具描述）收益尤其显著。
* **Cache 驱逐策略**：基数树节点用 LRU（最近最少使用）或引用计数管理，显存不够时优先驱逐最久未使用、且当前没有任何"正在进行中"的请求依赖它的节点。
* **调度器（Scheduler）**：SGLang 的调度器与 RadixAttention 深度耦合——调度时会优先把能复用同一前缀的请求安排在相近的时间处理，提升 cache 命中率，这是它在高并发结构化场景（如批量模板化 prompt、Agent 批量调用）下吞吐经常领先的原因之一。
* **前端 DSL**：除了作为推理引擎（runtime），SGLang 最初也是一门用于描述复杂 LLM 程序（多次生成、条件分支、并行采样、多轮交互）的前端语言，可以自动做批处理优化，这是它和 vLLM 定位上的差异点——vLLM 更纯粹是"推理服务"，SGLang 兼具"推理引擎 + 程序编排语言"的双重定位。
* **结构化输出**：内置对 JSON Schema/正则表达式约束解码的原生支持（结合 XGrammar 等语法约束库），在需要严格格式输出（function calling、JSON 模式返回）的场景中，解码效率和易用性通常优于外挂式方案。

### 6.5 vLLM vs SGLang vs TensorRT-LLM

| 维度 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 核心机制 | PagedAttention | RadixAttention | NVIDIA 官方 kernel + in-flight batching |
| 前缀/多轮复用 | Prefix Caching（新版本已相当自动化） | RadixAttention 原生、自动最大化复用 | 依赖手动优化，灵活性最低 |
| 结构化输出 | 支持（依赖 Outlines/XGrammar 等外部库集成） | 原生深度集成 | 支持但生态较少 |
| 性能 | 高，社区持续优化 | 在多轮对话/Agent/高并发结构化场景常有优势 | 单卡极致性能通常最优，尤其配合 TensorRT 编译优化 |
| 易用性/上手成本 | 最低，Python 生态友好 | 中等，需理解 RadixAttention/DSL 概念 | 最高，需要模型编译、TensorRT 引擎构建流程 |
| 生态与集成 | 最广泛（HuggingFace、各大云厂商默认支持），也是 verl/OpenRLHF 等 RL 框架常用的 rollout 引擎之一 | 增长最快，是 slime（THUDM）等新一代 RL 框架深度绑定的首选 rollout 引擎 | NVIDIA 生态，适合追求极限单卡吞吐/延迟、愿意接受工程成本的生产部署 |

### 6.6 批处理范式与 Chunked Prefill

* **Static Batching → Dynamic Batching → Continuous Batching**：静态批处理要求一批请求同时开始同时结束（等最慢的那个），动态批处理允许一批内请求长度不同但仍是"整批换入换出"，Continuous Batching（见 6.3）做到了单个请求粒度的即时换入换出，是当前主流范式。
* **Chunked Prefill**：一个长 prompt 的 Prefill 如果整体一次性执行，会独占 GPU 较长时间，阻塞同批次正在 decode 的请求（回忆 6.1 节：prefill 是大矩阵乘，decode 是逐 token 的小矩阵向量乘，混在一起调度时前者会让后者的延迟大幅劣化）。Chunked Prefill 把长 prefill 切成若干小块，穿插在 decode step 之间执行，平滑了 SLA（避免某个请求的长 prompt 让其它请求的 TPOT 突然飙升），vLLM 和 SGLang 均已支持。

### 6.7 投机解码（Speculative Decoding）家族

核心思想：Decode 阶段是 memory-bound（6.1 节已证明），意味着"算一个 token"和"并行算 $K$ 个 token 再验证"这两件事**读取权重和 KV Cache 的开销几乎一样**（都要把权重完整读一遍），但后者一次前向能产出多个候选 token 供验证——用这个"免费的并行度"换加速比。

* **Draft Model（投机采样鼻祖）**：用一个远小于目标模型的 draft 模型快速连续生成 $K$ 个候选 token，再用目标大模型对这 $K$ 个 token 做一次**并行**前向验证（数学上可证明，只要用恰当的拒绝采样规则，最终输出分布与直接用大模型逐 token 生成完全一致，不会因为引入 draft 而牺牲生成质量）。接受率越高（draft 模型猜得越准），单位大模型前向能"顺带"产出的 token 越多，加速比越高。

#### 深入：为什么投机解码不牺牲精度——Modified Rejection Sampling 完整算法

这是投机解码"无损"这个承诺背后真正的数学机制（Leviathan et al. 2023 / Chen et al. 2023 已核实的标准算法），值得完整过一遍，而不是当作黑盒信任：

设草稿模型（draft）在某个位置给出的分布是 $q(x)$，目标大模型（target）在同一位置给出的真实分布是 $p(x)$，draft 采样出的候选 token 是 $x$。验证步骤：

1. **接受判定**：以概率

$$\alpha = \min\left(1, \frac{p(x)}{q(x)}\right)$$

接受这个草稿 token。直觉上——如果目标模型认为这个 token 出现的概率**不低于**草稿模型给的概率（$p(x) \geq q(x)$），说明草稿"没有过度自信"，直接 100% 接受；如果目标模型认为这个 token 的真实概率**低于**草稿给出的概率（$p(x) < q(x)$），说明草稿模型对这个 token 有点"过度自信"了，就按 $p(x)/q(x)$ 这个比例打折接受（比值越接近 1 越倾向接受，比值越小越倾向拒绝）。
2. **拒绝后的残差重采样**：一旦某个位置被拒绝，草稿在这个位置往后的所有候选全部作废（因为它们都是基于这个被拒绝 token 生成的上下文，已经不可信），改为从一个**残差分布**：

$$p'(x) = \text{normalize}\left(\max(0,\ p(x) - q(x))\right)$$

里重新采样一个 token——即把目标分布里"被草稿分布低估的那部分概率质量"归一化后重新采样，直觉是"补上草稿模型漏掉/低估的可能性"。
3. **数学保证**：可以证明，按上述规则接受或重采样得到的 token，其边际分布**严格等于**直接用目标模型 $p$ 采样的分布，与草稿模型 $q$ 的好坏无关（$q$ 只影响接受率、也就是加速比，不影响最终输出的正确性）。这就是"投机解码是无损（lossless）加速"这一说法的完整数学依据，而不是一个近似或简化。

理解了这套机制就能明白，EAGLE、Medusa 等改进版本本质上都是在想办法**提升第 1 步里的接受率**（让草稿分布 $q$ 更接近目标分布 $p$），第 2/3 步的正确性保证是共享的、不需要因为换了草稿生成方式而重新论证。

* **Medusa**：不引入独立的 draft 模型，而是在目标模型基础上加装多个额外的解码头（head），每个头并行预测"当前位置往后第几个 token"，一次前向就能拿到多个位置的候选，再做树状验证，省去了维护和运行一个独立 draft 模型的开销。
* **EAGLE / EAGLE-2 / EAGLE-3**（已核实）：EAGLE 的核心洞察是"直接在 token 空间做草稿容易，但在**特征（feature）空间**做草稿准确率更高"——它复用目标模型**次顶层的隐藏状态特征**作为草稿模型的输入（而不是像传统 draft model 那样只用离散 token），因为这些特征包含了更丰富的上下文信息，让草稿预测更接近目标模型真实分布。EAGLE 采用**树状结构**的草稿（而非链式逐个候选），需要相应改造采样验证算法。效果上，目标大模型平均每次前向能产出 **3.2–4.5 个 token**（相比朴素逐 token 解码的 1 个），且研究发现"完全准确的特征序列"接受率显著高于"有一个特征出错的序列"，但 EAGLE 对特征误差有一定鲁棒性（不同误差程度间的接受率差异不算剧烈）。EAGLE-3 在此基础上进一步改进特征利用方式，在不改变模型输出分布的前提下持续提升加速比。
* **Lookahead Decoding**：不需要任何 draft 模型，利用 **Jacobi 迭代**的思路——把逐 token 串行解码问题重新表述为一个可以并行求解不动点的问题，通过维护多个"猜测轨迹"（n-gram 级别的候选延续）并行推进和验证，在没有额外小模型的情况下也能获得一定加速，代价是需要更多次的前向调用来收敛，适合没有合适 draft 模型可用的场景。

### 6.8 推理量化部署

* **AWQ（Activation-aware Weight Quantization，已核实机制）**：核心发现是"权重并不同等重要"——只保护约 1% 的显著权重（salient weight）就能大幅降低量化误差，而"显著"与否不是看权重本身的数值大小，是看**与它相乘的激活值通道的平均幅度**（激活值幅度大的通道，对应权重的微小误差会被放大，对输出影响更大）。具体做法是给每个通道找一个缩放系数 $s$，量化前用 $s$ 放大权重、量化后再用 $1/s$ 缩小激活值抵消（数学上等价变换，不改变原始计算结果，只改变量化时的数值分布），优化目标是最小化：

$$L(s) = \left\|Q(W\cdot\text{diag}(s))\cdot(\text{diag}(s)^{-1}\cdot X) - WX\right\|$$

其中 $Q(\cdot)$ 是量化函数，$X$ 是校准集上缓存的激活值。为了不做昂贵的全量搜索，AWQ 用一个简化技巧：直接用激活值每个通道的平均幅度 $s_X$ 作为"显著性"的代理指标，令

$$s = s_X^{\alpha}$$

只需要对**一个标量** $\alpha$ 做网格搜索（比较不同 $\alpha$ 下的重建误差，选误差最小的），而不用对每个通道单独搜索缩放系数，这是 AWQ 相比更早的量化方法能又快又准的关键简化。
* **GPTQ（已核实机制）**：源自 **OBQ（Optimal Brain Quantization）**——OBQ 的思路是量化一层的权重时**一次只量化一个权重**，每量化完一个就利用**二阶信息（Hessian）**去调整这一层里其余"尚未量化"的权重，补偿刚才那次量化引入的误差（如果不补偿，误差会在逐个量化的过程中累积放大）。该层的输出重建误差是权重的二次函数，对应的 Hessian 矩阵：

$$H = 2XX^{T}$$

（$X$ 是这一层的输入激活，只依赖激活不依赖权重，所以整层量化过程中 Hessian 是常量，只需要算一次）。OBQ 原始实现对 GPT-3 175B 这个规模要跑约 6 个月计算量，完全不现实。**GPTQ 的工程突破**：（1）不再按"哪个权重误差贡献最小就先量化哪个"这种自适应顺序，而是简单按固定顺序（比如从左到右）逐列量化，实验发现对大模型精度几乎没有影响，却把算法复杂度降了几个数量级；（2）用 **Cholesky 分解**预先算好整个 Hessian 逆矩阵所需的信息，避免在逐权重量化的过程中反复对海森矩阵求逆（数值上也更稳定，配合一个小阻尼项防止病态矩阵报错）；（3）批量化更新（lazy batch update），累积多列的补偿量后一次性更新，减少内存访问次数。这一整套优化把 OBQ 的"6 个月"压缩到几个 GPU-小时级别，是 GPTQ 能成为主流 4-bit PTQ 方案的核心原因，且全程不需要重新训练模型，只需要少量校准数据。
* **SmoothQuant**：解决激活值量化（而不仅是权重量化）的难点——LLM 的激活值经常出现少数异常大的通道（outlier），直接量化会造成巨大误差。SmoothQuant 的思路是把"量化难度"从激活值转移一部分到权重上（通过一个逐通道的缩放因子，数学上等价变换但改变了激活值和权重各自的数值分布特性），让两者都变得更容易量化，从而实现 **W8A8**（权重和激活都用 INT8）的高效部署。
* **不同量化组合的权衡**：**W4A16**（4-bit 权重、16-bit 激活，如 AWQ/GPTQ 常见配置）主要解决**显存容量**问题（权重变小，能塞进更小显存，且因为 decode 是 memory-bound，读取更小的权重直接提升 decode 吞吐），对算力几乎没有额外要求；**W8A8**（如 SmoothQuant）额外利用 INT8 Tensor Core 算力，在 compute-bound 的 Prefill 阶段也能提速；**FP8**（Hopper/Blackwell 原生支持）在精度和速度上通常优于 INT8 方案，是当前新硬件上的主流选择，可以做 per-tensor（整个 tensor 一个缩放因子，最简单但精度最低）、per-token（每个 token 独立缩放，更精细）等不同粒度；**KV Cache 量化**是独立于权重量化的另一个维度（见 6.2 节），三者可以自由组合，具体选择取决于瓶颈到底在显存容量、显存带宽还是算力。

### 6.9 P/D 分离与 Mooncake

**P/D Disaggregation** 的动机在 6.1 节已经论证清楚：Prefill compute-bound、Decode memory-bound，混在同一批卡上调度会互相干扰（长 prefill 挡住正在 decode 的请求，破坏 TTFT/TPOT SLA）。解法是把两者部署到不同卡池，Prefill 完成后通过高速互联把 KV Cache 传给 Decode 池，两边可以独立扩缩容、独立选型。

**Mooncake**（已核实，Moonshot AI 旗下 Kimi 的服务平台架构，论文获 FAST 2025 最佳论文奖）的关键设计：

* 提出以 **KVCache 为中心的分离式架构**（KVCache-centric Disaggregated Architecture），把 Prefill 集群和 Decoding 集群彻底分开；
* 核心组件是 **KVCache-centric 调度器**，目标是在满足延迟相关 SLO 的前提下，最大化整体有效吞吐；
* 充分利用 GPU 集群里原本被低估利用的 CPU、DRAM、SSD 资源，实现跨节点的分布式 KVCache 缓存（不只是 GPU 显存内的 cache，而是一个跨设备的多级缓存池）；
* 实测在长上下文场景下优势尤其明显（长上下文意味着 KV Cache 更大、Prefill 更昂贵，P/D 分离和跨节点缓存复用的收益也更大）；
* 其核心传输组件 **Transfer Engine** 已独立开源，SGLang 等推理引擎已经把 Mooncake 的 Transfer Engine 作为 P/D 分离场景下的 KV Cache 传输后端集成进来。

vLLM 和 SGLang 目前均已支持 P/D 分离部署模式，Mooncake 代表的"以 KVCache 而非计算为核心资源"的架构思路，是理解这一代推理系统设计哲学转变的关键案例。

### 6.10 Multi-LoRA Serving 与服务化 SLO

* **Multi-LoRA Serving**：一个 base model 权重常驻显存，同时服务成百上千个不同的 LoRA adapter，请求粒度动态切换使用哪个 adapter。LoRA 的计算本质是

$$Y = XW + X(BA)$$

（$W$ 是 base 权重，$B$、$A$ 是低秩的 adapter 矩阵，$\text{rank}$ 通常只有几到几十），如果朴素实现——同一个 batch 里 $N$ 个请求用了 $N$ 个不同的 adapter，就要发起 $N$ 次独立的小矩阵乘 kernel（每次调用的矩阵都很小，GPU 利用率低，kernel 启动开销占比高）。**S-LoRA**、**Punica** 的核心优化是把"同一 batch 内多个不同 adapter 的矩阵乘"重新组织成一次**批量间隔矩阵乘（Batched/Segmented GEMM）**调用——base 权重部分 $XW$ 本来就是所有请求共享的一次大矩阵乘；额外的 $X(BA)$ 部分虽然每个请求的 $B$、$A$ 不同，但由于 $\text{rank}$ 很小，可以把不同请求的 $A$、$B$ 分别拼接、用定制 kernel 一次性算完所有请求各自对应的低秩增量，而不是发起 $N$ 次独立 kernel，显著提升吞吐（尤其是 adapter 数量多、每个 adapter 服务请求数不均匀的场景）。
* **Request Scheduler 与 SLO**：在线服务通常同时优化 **TTFT（Time To First Token，首 token 延迟，主要受 Prefill 排队和执行时间影响）** 和 **TPOT（Time Per Output Token，逐 token 延迟，主要受当前 decode batch 大小和 KV Cache 读取带宽影响）** 两个指标，两者存在权衡（更大的 batch 提升整体吞吐但会拉长单个请求的 TPOT），调度器需要在两者之间根据 SLO 目标动态调整（比如给高优先级请求抢占式插队，牺牲部分低优先级请求的 TPOT 保证高优先级请求的 TTFT）。

## 7. 后训练：SFT 与 RL 框架体系

大模型的"后训练"（Post-Training）已经从 RLHF 单一流程演化成一整套系统工程，2024-2026 年是 RL 训练系统快速迭代的阶段（DeepSeek-R1 之后尤其明显），核心矛盾是：**RL 训练在一个循环里同时需要"训练"（梯度更新，显存密集）和"推理"（rollout 生成，吞吐密集）两种截然不同的计算模式**，这决定了 RL 框架的系统设计比纯 SFT 复杂得多。

### 7.1 SFT：后训练的第一步

在指令数据上做标准的下一 token 预测微调，技术上和预训练没有本质区别，但有几个工程细节值得注意：

* **Loss Masking**：对话数据里通常只对"模型应该生成的部分"（assistant 的回复）计算 loss，用户输入部分的 token 虽然要参与前向（提供上下文），但不贡献梯度，需要在数据处理时精确构造 loss mask。
* **Sequence Packing**：不同对话样本长度差异很大，如果按固定长度 padding，会浪费大量计算在 padding token 上；Packing 把多条短样本拼接进一个固定长度的序列里（用 attention mask 保证样本间不互相"看到"），显著提升有效计算的占比，是训练吞吐优化的重要手段。

### 7.2 RLHF 经典三段式（PPO）：完整拆解

InstructGPT 确立的范式：SFT → 训练 Reward Model（用人类偏好对比数据） → **PPO** 用 RM 打分驱动策略更新。PPO 阶段需要同时维护**四个模型**：

* **Actor（策略模型）**：正在被训练、要生成回复的模型，初始化自 SFT 模型；
* **Critic（价值模型）**：估计"当前状态未来还能拿到多少期望回报"，用于计算优势函数（Advantage），减少训练方差，通常初始化自 Reward Model；
* **Reward Model**：对 Actor 生成的完整回复打一个标量分数，代表人类偏好；
* **Reference Model**：初始化后就冻结不再更新的 SFT 模型副本，用于约束 Actor 不要偏离原始分布太远（防止 reward hacking，即模型学会用一些"投机取巧"的方式骗高分而输出质量实际下降）。

**PPO 目标函数**：

$$L(\theta) = \mathbb{E}\left[\min\Big(r(\theta)\cdot A,\ \text{clip}(r(\theta),\ 1-\epsilon,\ 1+\epsilon)\cdot A\Big)\right] - \beta \cdot D_{KL}(\pi_\theta \,\|\, \pi_{ref})$$

其中重要性采样比

$$r(\theta) = \frac{\pi_\theta(y|x)}{\pi_{\theta_{old}}(y|x)}$$

是新旧策略在同一动作上的概率比值，$A$ 是优势函数（这个动作比"平均水平"好多少，由 Critic 估计得到，常用 GAE 广义优势估计平滑）。**clip 项的作用**：如果 $r(\theta)$ 因为某次更新走得太远（新策略和旧策略概率比值偏离 1 太多），就把它限制在 $[1-\epsilon, 1+\epsilon]$ 区间内，防止单次更新步子迈得过大导致训练不稳定——这是"Proximal"（近端）这个名字的来源，即每次更新都被约束在旧策略的"邻近"范围内。**KL 惩罚项**进一步约束 Actor 别偏离 Reference Model（即最初的 SFT 模型）太远，是防止模型退化/reward hacking 的第二道防线。

四个模型 + 在线生成（每个训练迭代都要用当前 Actor 现场生成回复，再算 reward、算 advantage、再更新）使得 PPO 的显存开销和系统复杂度远高于普通 SFT，这也是后续 DPO、GRPO 等方法试图简化的地方。

#### 深入：GAE 怎么算优势函数、一次 PPO 迭代的完整流程

**优势函数 $A$ 为什么不能直接用 reward**：一条生成的回复只有在**结束时**才拿到 Reward Model 打的一个标量分数，但策略更新需要知道"生成过程中每一步（每个 token）的选择好不好"，直接把整条回复的最终 reward 均摊给每个 token 会引入很大方差（一条回复里可能有的 token 选得好、有的选得一般，但都背了同一个最终分数）。**GAE（Generalized Advantage Estimation，广义优势估计）**的解法：先定义单步 TD 误差：

$$\delta_t = r_t + \gamma V(s_{t+1}) - V(s_t)$$

（$V$ 是 Critic 估计的价值函数，$r_t$ 是这一步的即时奖励，语言模型场景里通常只有最后一步有非零 reward、中间步的 $r_t$ 常设为 0 或来自逐 token 的 KL 惩罚），再把多步 TD 误差按指数衰减加权求和：

$$A_t^{\text{GAE}} = \sum_{l=0}^{\infty} (\gamma\lambda)^l \cdot \delta_{t+l}$$

其中 $\gamma$ 是折扣因子，$\lambda$ 是 GAE 特有的调节参数，控制"偏差-方差"的权衡——$\lambda=0$ 时退化为只用单步 TD 误差（方差小但偏差大，因为完全依赖可能不准的 Critic 估计），$\lambda=1$ 时退化为蒙特卡洛整条轨迹的真实回报减基线（偏差小但方差大，因为依赖一整条随机轨迹的实现）。GAE 通过 $\lambda$ 在两者之间插值，是"用 Critic 的估计降方差、又不完全依赖 Critic 引入偏差"的折中方案。Critic 本身也需要训练，其损失就是让 $V(s_t)$ 去回归实际观测到的回报（value loss，通常是均方误差）。

**一次 PPO 迭代的完整流程（伪代码级）**：
1. 从 prompt 数据集采样一批 prompt；
2. 用**当前** Actor 对每个 prompt 生成完整回复（这一步在系统上就是一次推理 rollout，通常由 vLLM/SGLang 承担，见第 7.5 节起的系统架构）；
3. 用 Reward Model 对每条完整回复打分；
4. 用 Reference Model 和 Actor 分别对生成的每个 token 算 log 概率，两者之差乘以系数构成逐 token 的 KL 惩罚（防止偏离过远），通常并入 reward 信号；
5. 用 Critic 对每个 token 位置估计 $V(s_t)$，结合第 4 步的（近似）reward 序列，按 GAE 公式算出每个 token 的优势 $A_t$；
6. 用上面的 PPO clip 目标函数更新 Actor，用 value loss 更新 Critic（可能会对同一批 rollout 数据做多个 epoch 的更新，但每次更新后重要性采样比 $r(\theta)$ 会偏离 1 越来越多，clip 机制正是为了约束这种偏离）；
7. 回到第 1 步，用**更新后**的 Actor 进行下一轮 rollout。

这个"生成 → 打分 → 算优势 → 更新 → 再生成"的循环，正是第 7.5 节要讨论"训练和 rollout 如何在系统层面协同"的问题根源——第 2 步是推理负载、第 6 步是训练负载，两者计算特性完全不同，却要在同一个迭代循环里紧密配合。

### 7.3 DPO：把 RL 问题变成监督学习问题

**推导思路（已核实的标准推导链条）**：

1. RLHF 的优化目标（最大化 reward 同时被 KL 项约束在 reference 附近）存在一个**解析解**——对于给定的 reward 函数 $r(x,y)$，最优策略 $\pi^*(y|x)$ 可以用 reference 策略 $\pi_{ref}(y|x)$ 和 reward 表示出来（配分函数 $Z(x)$ 是一个难以计算的归一化项）。
2. 把这个解析解**反过来**，可以从任意策略 $\pi_\theta$ 反解出一个"隐式 reward"：

$$r_\theta(x,y) = \beta\left[\log \pi_\theta(y|x) - \log \pi_{ref}(y|x)\right]$$

也就是说，**策略模型本身隐含定义了一个 reward 函数**，这正是 DPO 论文标题"Your Language Model is Secretly a Reward Model"的含义。
3. 把这个隐式 reward 代入 **Bradley-Terry 偏好模型**（一个描述"给定两个选项，人类更偏好其一"的经典概率模型）：

$$P(y_w \succ y_l) = \sigma\big(r(x,y_w) - r(x,y_l)\big)$$

（$\sigma$ 是 sigmoid 函数），代入后配分函数 $Z(x)$ 会在相减时**自动抵消**（因为 $Z(x)$ 只依赖 $x$ 不依赖 $y$，两个 reward 相减时抵消掉了），得到一个不再需要显式训练/维护 Reward Model 的损失函数。
4. 最终的 **DPO Loss**：

$$\mathcal{L}_{DPO} = -\mathbb{E}\left[\log\sigma\left(\beta\log\frac{\pi_\theta(y_w|x)}{\pi_{ref}(y_w|x)} - \beta\log\frac{\pi_\theta(y_l|x)}{\pi_{ref}(y_l|x)}\right)\right]$$

其中 $y_w$ 是人类偏好数据里的"更优回复"、$y_l$ 是"更差回复"。这本质上是一个**二分类交叉熵损失**：模型只需要学会让"更优回复相对 reference 的对数概率提升幅度"大于"更差回复相对 reference 的提升幅度"即可。

**工程含义**：DPO 全程不需要在线采样（不需要现场生成回复）、不需要训练和维护独立的 Reward Model、不需要 Critic，只需要一份离线的偏好数据对（prompt、好回复、差回复）就能像普通监督学习一样训练，系统复杂度和显存开销远低于 PPO。代价是它是**离线（offline）算法**——完全依赖预先收集好的偏好数据，无法像在线 RL 那样让模型在训练过程中探索并从"自己生成的、新出现的错误模式"中学习，理论上限通常不如设计良好的在线 RL。

**从梯度角度理解 DPO 在学什么**：把 DPO loss 对参数 $\theta$ 求梯度，可以整理成这样一个直觉形式——梯度方向是"提高好回复概率、降低差回复概率"的组合，但每个样本对梯度的**贡献权重**正比于：

$$\sigma\big(\hat r_\theta(x,y_l) - \hat r_\theta(x,y_w)\big)$$

也就是"当前隐式奖励模型把这一对样本判断错的程度"（如果模型已经很确信好回复比差回复好，这一项接近 0，梯度贡献很小；如果模型现在还判断反了或者信心不足，这一项接近 1，梯度贡献大）。这和普通交叉熵分类器的行为是一致的——**模型会自动把更多梯度信号花在"当前还没学对"的样本上**，这也是为什么 DPO 训练中后期 loss 下降会变慢（大部分样本已经被"学对"，贡献的梯度权重自然衰减），是判断 DPO 训练是否正常收敛时的一个有用直觉。

### 7.4 GRPO：DeepSeek 的 Critic-Free 方案

**GRPO（Group Relative Policy Optimization，DeepSeekMath 论文提出，DeepSeek-R1 推理能力训练的核心算法，已核实）** 目标函数：

$$J_{GRPO}(\theta) = \mathbb{E}_{q\sim P(Q),\ \{o_i\}\sim\pi_{old}(O|q)}\left[\frac{1}{G}\sum_{i=1}^{G}\left(\min\Big(\rho_i A_i,\ \text{clip}(\rho_i, 1-\epsilon, 1+\epsilon)A_i\Big) - \beta D_{KL}(\pi_\theta\|\pi_{ref})\right)\right]$$

其中重要性采样比

$$\rho_i = \frac{\pi_\theta(o_i|q)}{\pi_{old}(o_i|q)}$$

和 PPO 一样，clip 机制也和 PPO 相同。**核心区别在优势函数 $A_i$ 的计算方式**：GRPO **完全去掉了 Critic 模型**，对同一个 prompt $q$，用当前策略采样出一**组**（group，共 $G$ 个）不同的回复 $\{o_1, \ldots, o_G\}$，各自拿到标量得分 $\{r_1, \ldots, r_G\}$（可以来自 Reward Model，也可以来自规则化验证器），把**这一组内的相对好坏**做归一化直接当作每个回复的优势估计：

$$A_i = \frac{r_i - \text{mean}(\{r_1,\ldots,r_G\})}{\text{std}(\{r_1,\ldots,r_G\})}$$

即"这个回复比同一 prompt 下这一组回复的平均水平好多少个标准差"，不再需要 Critic 网络单独学习"预期回报"这件事——本质上是用**同一 prompt 下的组内采样均值**直接顶替了 PPO 里需要专门训练一个 Critic 网络才能得到的"状态价值基线"，因为同一个 $q$ 下的这组回复本来就是较自然的对照组（相同的题目/上下文，比较"哪个解法更好"远比让 Critic 去预测一个抽象的期望回报更直接、更省资源）。这也解释了为什么 GRPO 对可验证奖励任务特别友好：一道数学题采样 $G$ 个不同解法，算对的分数高、算错的分数低，组内一归一化立刻就有了清晰的相对优劣信号，完全不需要 Critic。

**这个设计的意义**：

* **显存直接减半以上**：PPO 需要同时维护 Actor + Critic + Reward Model + Reference（Critic 通常和 Actor 差不多大），GRPO 去掉 Critic 后，只需要 Actor + Reference（+ Reward Model 或直接用规则化验证器），大幅降低了大规模 RL 训练的显存/工程开销；
* **天然适配"可验证奖励"场景**：数学题、代码题这类任务的答案对错可以用规则直接判断（而不需要训练一个学习到的 Reward Model），GRPO 的"组内相对比较"思路和这种场景高度契合——对同一道题采样 $G$ 个不同解法，能算对的给高分、算错的给低分，组内一比较就得到了优势信号，不需要 Critic 去估计"这道题平均能得多少分"；
* 这正是 **RLVR（Reinforcement Learning with Verifiable Rewards，基于可验证奖励的强化学习）**成为 R1 之后重要趋势的原因——越来越多推理任务的 RL 训练直接用规则化验证器（答案是否正确、代码是否通过测试）替代学习到的 Reward Model，进一步简化了系统（不需要训练和部署额外的 RM），GRPO 的算法设计和这一趋势相互成就。

### 7.5 RL 训练系统的两根设计轴

理解各框架前，先理解两个关键设计轴，后面每个框架的差异基本都能归结到这两根轴上的取舍：

1. **Colocate（同卡复用）vs Disaggregate（训练/rollout 分离部署）**：
   * Colocate：同一批 GPU 交替承担训练和 rollout（生成）任务，通过显存 offload/reload 在两种角色间切换，硬件利用率高但调度复杂，训练引擎和推理引擎的权重需要频繁同步。
   * Disaggregate：训练卡池和 rollout 卡池物理分离，rollout 池持续跑 vLLM/SGLang 生成，训练池持续跑 Megatron/FSDP 更新参数，通过权重广播（NCCL broadcast 或 checkpoint 同步）定期把最新策略权重发给 rollout 池。可以独立扩缩容，是大规模场景的趋势方向。
2. **同步 RL vs 异步 RL**：同步（严格 on-policy）每一轮都要等所有 rollout 完成才能更新（等待长尾请求——某些回复特别长，其它已经生成完的请求所在的 GPU 只能空闲等待），GPU 利用率受限；异步 RL 允许训练和生成流水线重叠（用一定程度的 off-policy 换取吞吐），是超大规模 RL 训练提升 MFU 的关键方向，AReaL（见 7.11 节）是这一方向的代表性工作。

### 7.6 verl（字节跳动，HybridFlow）

**已核实的关键信息**：verl 是由字节跳动 Seed 团队发起、目前由 verl 社区维护的开源 RL 训练库，是论文《HybridFlow: A Flexible and Efficient RLHF Framework》的开源实现，目前是开源社区里生态最活跃的 RL 训练框架之一。

* **核心设计——混合编程模型（Hybrid Programming Model）**：结合了 **Single-Controller**（单控制器，编排逻辑集中、代码直观、易调试和扩展新算法）和 **Multi-Controller**（多控制器，各 Worker 独立高效执行，避免中心节点成为瓶颈）两种范式各自的优势——上层用单控制器的方式描述数据流（用几行代码就能表达 PPO、GRPO 等复杂的 RL dataflow），底层各 Worker 各自独立高效执行，兼顾了灵活性和执行效率。
* **解耦计算与数据依赖**：这使得 verl 能无缝对接现有的各类 LLM 框架——训练后端可选 **FSDP** 或 **Megatron-LM**，rollout（生成）后端可选 **vLLM** 或 **SGLang**，支持把不同角色的模型灵活放置到不同 GPU 集合上（对应 7.5 节的 colocate/disaggregate 选择），可以根据集群规模灵活伸缩。
* **性能**：论文报告相比当时的 SOTA baseline，在运行各类 RL(HF) 算法时训练吞吐提升 **$1.5\times$ 到 $20\times$**。
* **算法支持**：PPO、GRPO、DPO、RLOO 等主流后训练算法均已支持，对可验证奖励（数学/代码 RLVR）场景有专门优化路径。

### 7.7 slime（智谱 AI / THUDM，SGLang 原生）

**已核实的关键信息**：slime 由 THUDM（清华大学知识工程实验室 / 智谱 AI 技术脉络）开源，是一个面向 **RL Scaling** 的 LLM 后训练框架，是智谱 AI GLM 系列模型（**GLM-4.5、GLM-4.6、GLM-4.7、GLM-5、GLM-5.1、GLM-5.2** 等）实际使用的后训练技术栈。

* **三大核心模块**：
  1. **训练模块**：基于 **Megatron** 处理主要的学习/梯度更新过程；
  2. **rollout 模块**：基于 **SGLang** 生成新数据（与 SGLang 深度绑定，而不是像大多数框架那样把 SGLang 作为"可选后端之一"）；
  3. **Data Buffer**：管理 prompt 初始化、自定义数据生成、reward 计算、verifier 反馈、环境交互等，训练模块和 rollout 模块都通过统一的 training/rollout/Data Buffer 数据路径交互。
* **生产验证的性能**：GLM-5.2 是一个 **7500 亿参数的稀疏 MoE 模型**，其**整个后训练阶段在这套框架上只花费约 2 天**，这个速度对于这个规模的稀疏 MoE 模型而言相当突出，直接体现了"Megatron 训练 + SGLang rollout 深度耦合"这一设计路线在超大规模场景下的工程价值。
* **与 verl 的关系**：两者都在解决"训练引擎 + 推理引擎异构编排"这个核心问题，verl 更早开源、生态更广、训练/rollout 后端的可插拔性更强（FSDP/Megatron 二选一，vLLM/SGLang 二选一）；slime 则更聚焦在"Megatron + SGLang"这一条路径上做极致的性能优化，尤其是超大规模 MoE 场景（GLM-5.2 这种 750B 参数量级），可以理解为在通用性和极致性能之间，slime 选择了向后者倾斜。

### 7.8 ms-swift（魔搭 ModelScope Swift，阿里）

**已核实的关键信息**：ms-swift 是 ModelScope（魔搭）社区推出的大模型与多模态大模型训练部署框架（AAAI 2025 收录），是一个覆盖面远比 verl/slime 更广的**统一工具箱**——CPT（继续预训练）/SFT/DPO/GRPO 等全流程，覆盖 **600+ LLM**（Qwen 系列、DeepSeek 系列、GLM 系列、InternLM、Llama 等）和 **300+ 多模态大模型**（Qwen-VL、InternVL、Ovis、Gemma、Llava、Phi 等）。

* **RLHF 算法支持**：DPO、GRPO、**DAPO**（一种在 GRPO 基础上进一步优化的算法变体）、RM（Reward Model 训练）、PPO、KTO 等，覆盖纯文本和多模态大模型两类场景。
* **训练方式**：全参数微调、LoRA、QLoRA、DoRA 等轻量化微调技术开箱即用。
* **分布式技术**：支持 DDP、`device_map`、DeepSpeed ZeRO-2/ZeRO-3、FSDP，并且**集成了 Megatron 的并行技术**（张量并行、流水线并行、序列并行、专家并行），用 Megatron 并行来加速 CPT/SFT/DPO/GRPO 在大模型上的训练。
* **硬件覆盖**：CPU、RTX 消费级显卡、T4/V100、A10/A100/H100，以及**华为昇腾 NPU**、Apple MPS 等，硬件适配面在同类框架里也是最广的之一。
* **定位判断**：相比 verl/slime 在超大规模 RL 系统性能上的极致打磨，ms-swift 的核心卖点是**极广的模型覆盖面 + 极低的上手门槛**（命令行/YAML 配置即可跑通训练），对个人开发者和中小团队的友好度更高；超大规模（千卡级）RL 训练场景，目前工业界更常见的选择仍然是 verl/slime 这类专注系统性能的框架。

### 7.9 OpenRLHF（Ray + vLLM + DeepSpeed）

**已核实的关键信息**：OpenRLHF 是较早期出现、被称为"首个高性能生产级开源 RLHF 框架"之一，代表性地验证了 **Ray + vLLM 分布式架构** 这一组合范式的可行性——后续很多框架（包括 verl）在设计思路上受其影响。

* **架构**：用 **Ray** 做分布式调度编排，用 **vLLM** 承担 rollout（生成）任务（低显存开销、高吞吐生成），用 **DeepSpeed ZeRO** 承担训练侧的 3D 并行（张量、数据、序列并行）。
* **GPU 角色划分**：明确把 GPU 分成两类角色——**rollout engine**（专门负责生成回复）和 **actor engine**（负责算 log-probability 和实际的模型训练更新），这是"训练/rollout 分离"思路的早期实践者之一。
* **序列并行**：用 **Ring Attention** 承担序列并行部分，配合 DeepSpeed-ZeRO 实现长序列场景下的高效训练。
* **统一 Agent 范式**（较新版本）：采用 token-in-token-out 的统一流水线，把"执行模式"（单轮/多轮对话）和"RL 算法"解耦，任意算法可以搭配任意执行模式，通过一套共享的 loss 层实现，便于扩展支持 Agentic RL 等新场景。
* **算法覆盖**：PPO、DAPO、REINFORCE++ 等，也支持多模态（VLM）和异步 RL。

### 7.10 ChatLearn（阿里云 PAI）

**已核实的关键信息**：ChatLearn 是阿里云 PAI 平台推出的大规模对齐任务训练框架。

* **编程模型**：用户只需要为每个模型（Actor/Reward/Critic/Reference 等）包装几个函数，系统自动接管资源调度、数据流和控制流传输、分布式执行的复杂性，降低了多模型协同训练的编码负担。
* **训练方法**：支持 RLHF、DPO、OnlineDPO、GRPO 等，同时支持用户自定义执行流程。
* **后端可插拔**：训练可选 Megatron-LM、DeepSpeed 等计算后端，推理（rollout）可选 vLLM、SGLang（通过 `runtime_args.rollout_engine` 参数配置），并支持 sequence packing、Ulysses 序列并行、Group GEMM 等训练加速技术。
* **实测性能**：论文报告在 7B+7B（Policy+Reward）规模下有 **52%** 的性能提升，在 70B+70B 规模下有 **137%** 的性能提升（相比对照基线），并支持超过 **600B 参数**规模的 RL 训练。

### 7.11 AReaL（清华大学 / 蚂蚁研究院 / 香港科技大学）

**已核实的关键信息**：AReaL 是一个**完全异步**的强化学习系统，由清华大学交叉信息研究院（IIIS）、蚂蚁研究院（Ant Research）、香港科技大学联合研发，专门面向大规模推理模型（reasoning model）的高效训练，是"异步 RL"方向最具代表性的开源工作（NeurIPS 2025 收录）。

* **要解决的问题**：现有大规模 RL 系统大多是**同步**的——生成（rollout）和训练在一个批次内交替进行，必须等批次内**最长的输出**生成完才能进入训练阶段，这种"批内同步"在数学/代码推理任务中问题尤其严重（不同难度的题目生成长度差异极大），导致大量 GPU 在等待过程中空闲。
* **解法**：**彻底解耦生成和训练**——rollout worker 持续不断地生成新输出，不用等待，训练 worker 只要攒够一批数据就立刻更新模型，两者异步并行流水线运行。
* **稳定性保障**：因为异步执行意味着用于训练的样本可能是"过时"的（用旧版本的策略生成，而当前策略已经更新了几步），AReaL 通过**平衡 rollout 和训练 worker 的工作负载来控制数据陈旧度（staleness）**，并采用一种**staleness-aware（陈旧度感知）的 PPO 变体**来更好地处理过时样本，避免训练不稳定。
* **实测效果**：在数学和代码推理基准测试中，相同 GPU 数量下相比同步系统实现最高 **$2.77\times$** 的训练加速，且最终模型效果与同步方案持平甚至更好。

### 7.12 其它值得了解的框架

* **TRL（HuggingFace）**：`SFTTrainer`/`DPOTrainer`/`PPOTrainer`/`GRPOTrainer` 等，和 `transformers`/`accelerate`/`peft` 生态无缝衔接，API 最简单、上手最快，但分布式扩展性和大规模 rollout 性能不是它的设计重点，适合快速实验和中小规模训练。
* **NeMo-Aligner（NVIDIA）**：基于 NeMo/Megatron 生态的对齐训练框架，与 NVIDIA 软硬件栈（TransformerEngine、TensorRT-LLM 推理）绑定较深，适合已经在 NeMo 体系里的团队。

### 7.13 权重同步：RL 系统里最容易被忽视的工程细节

Actor（训练中的策略模型）每次梯度更新后，rollout 引擎（vLLM/SGLang）里缓存的模型权重就过期了，必须同步最新权重才能保证 on-policy（或至少近似 on-policy，异步系统里允许一定滞后）。这个"训练引擎 → 推理引擎"的权重同步是 RL 系统里容易被低估的性能瓶颈：

* **Colocate 场景**：训练和 rollout 共享同一批 GPU，权重同步可以直接在显存内做 NCCL broadcast，速度快但需要精细的显存管理（训练态——参数+梯度+优化器状态，和推理态——KV Cache+推理引擎自身的显存池，两种状态的显存占用曲线完全不同，角色切换时容易 OOM，需要精心设计 offload/reload 的时序）。
* **Disaggregate 场景**：训练卡池和 rollout 卡池物理分离，需要跨卡池传输权重（跨节点组的 NCCL 广播，或落盘 checkpoint 再由 rollout 侧加载），大模型（尤其是像 GLM-5.2 这种 750B 参数的 MoE 模型）的同步延迟会直接拖慢整个 RL 迭代周期，是 verl、slime、ChatLearn 等框架重点优化的系统环节之一——slime 之所以能把 750B MoE 模型的完整后训练压缩到约 2 天，权重同步效率的极致优化是背后的关键工程贡献之一。

## 8. 训练与推理的边界正在模糊

值得建立的一个系统性认知：2024 年后，"训练系统"和"推理系统"不再是两条独立的技术栈——

* RL 训练系统本身就是训练引擎（Megatron/FSDP）+ 推理引擎（vLLM/SGLang）的耦合体，推理引擎的调度、批处理、KV Cache 能力直接决定 RL 训练的吞吐上限（slime 绑定 SGLang、多数框架把 vLLM/SGLang 都列为一等公民后端，都是这个逻辑的体现）；
* 推理引擎反过来也在吸收训练系统的并行技术：大模型推理的多卡 TP/PP 部署直接复用了 Megatron 式的切分思路，大模型 MoE 推理的 EP 也直接对应训练时的专家并行（甚至可以共用 DeepEP 这类通信库）；
* 未来看这个方向的资料，建议同时关注训练侧和推理侧的进展，二者会持续互相渗透——例如推理引擎的投机解码技术反哺 RL 中 rollout 阶段的生成加速，训练中沉淀的量化/压缩技术反哺推理部署，P/D 分离这类推理系统架构的设计思路也在影响 RL 系统里 colocate/disaggregate 的取舍。

## 9. 实战路径建议

1. **Level 1（并行策略手感）**：单机多卡，先跑通 DDP 微调一个几亿参数模型，用 Nsight Systems 观察一次 Ring All-Reduce 的两阶段耗时；再切到 FSDP2/ZeRO-3 跑同样任务，对比显存曲线（用 `torch.cuda.memory_summary()` 或 profiler），直观验证"分片 vs 复制"的差异，以及"用时聚合、算完释放"的显存节奏。
2. **Level 2（3D 并行）**：在 2-8 卡上用 Megatron-LM（或 torchtitan）跑通 TP+PP+DP 组合，用 NSYS 观察 All-Reduce/P2P 通信与计算的 overlap 情况，手动统计一次迭代里 PP 的 bubble 时长，验证是否接近 $\frac{P-1}{M}$ 的理论比例，再尝试 1F1B → Interleaved 1F1B 切换后 bubble 的变化。
3. **Level 3（推理引擎）**：本地起一个 vLLM 和一个 SGLang 服务，同一模型下用相同压测脚本（不同并发、不同前缀共享比例）对比吞吐/TTFT/TPOT，直观感受 RadixAttention 在多轮对话场景下相比朴素 Prefix Caching 的优势；再手动计算一下你测试模型的 KV Cache 理论大小（用 6.2 节的公式），和实际观测到的显存占用做对照。
4. **Level 4（投机解码）**：在 vLLM 或 SGLang 上开启一种投机解码方案（draft model 或 EAGLE），对比开启前后的吞吐和平均每次前向产出 token 数，验证是否接近论文报告的加速比量级。
5. **Level 5（后训练全流程）**：用 ms-swift 或 TRL 跑通一次完整的 SFT → DPO/GRPO 流程（小模型、小数据即可），观察 DPO 训练时 loss 曲线和"chosen/rejected 概率差值"的变化；再尝试用 verl 在一个可验证奖励任务（如数学题）上跑通一次 GRPO 训练，观察 rollout 阶段和训练阶段的耗时占比、GPU 利用率曲线，感受"RL 训练 = 推理吞吐 + 训练吞吐"这个系统性认知。
6. **Level 6（系统调优）**：给 Level 5 的 RL 训练换上 colocate/disaggregate 两种部署模式，对比端到端吞吐，理解权重同步开销在真实系统里的量级；如果条件允许，进一步尝试异步 RL（对照 AReaL 的思路）对吞吐的影响。
